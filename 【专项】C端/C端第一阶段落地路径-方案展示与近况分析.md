# C端第一阶段落地路径：方案展示与近况分析

> 第一阶段目标：先串通 C 端第一条线，让患者能看到当前正在生效的干预方案，并在首页通过“近况分析”被引导去阅读方案。

## 1. 原型依据

来自 2.0 原型的关键判断：

1. 慢管的核心是 AI 共管闭环：健康档案/随访/指标/饮食运动记录 → AI 生成成果物 → AI 生成 TodoList → 患者执行 → 新数据回流。
2. 管理端的干预方案已改为“一类方案一行记录”，每类方案独立制定、独立生效。
3. C 端点击后查看“患者正在生效中的干预方案”。
4. C 端方案详情需要兼容三种内容形态：
   - 根据患者体重等数据智能推荐出来的食谱，兼容老数据。
   - 管理端通过纯文本制定的方案，兼容老数据。
   - AI 共创的大 JSON 渲染出的 HTML，本期新增方向。
5. 原型中已提到：食谱、监测方案最终会在待办任务中体现出来，不只以食谱或计划文本存在。

因此第一阶段不能直接跳到 TodoList 或 AI 健管师，而应该先让“干预方案成果物”在 C 端可见、可理解、可进入。

## 2. 本阶段要解决的问题

### 患者侧问题

患者现在需要知道：

1. 我现在有几份正在生效的干预方案。
2. 分别是什么类型的方案。
3. 这些方案是谁为我制定的，什么时候生效。
4. 我应该先看哪一份。
5. 如果没有方案，我接下来应该做什么。

### 产品侧问题

C 端需要先建立“方案展示容器”，后面才能承接：

1. 待办任务从方案中生成。
2. AI 健管师基于方案做解读。
3. 首页近况分析基于方案给出提醒。
4. 患者执行后数据回流，再影响下一轮方案和分析。

## 3. 第一阶段页面范围

本阶段只做最小闭环，不扩散。

| 页面 | 是否新增/改造 | 作用 |
| --- | --- | --- |
| 首页 | 改造 | 增加近况分析，提示当前生效方案数量，引导阅读 |
| 干预方案列表 | 新增/重构 | 展示患者当前生效中的各类方案 |
| 干预方案详情 | 新增/重构 | 展示单个方案完整内容 |
| 空状态页/空状态模块 | 新增 | 无生效方案时引导记录指标或联系团队 |

暂不做：

1. 待办任务模块。
2. AI 健管师解读。
3. 动态表单。
4. 复杂个性化推荐。

这些放到后续节奏中。

## 4. 首页：近况分析

### 首页模块目标

近况分析第一阶段不要做成复杂健康评分，也不要过度医疗判断。它先承担三个作用：

1. 告诉患者当前有几份生效方案。
2. 提醒患者这些方案和最近健康管理有关。
3. 引导患者点击查看方案。

### 推荐文案结构

```text
近况分析
当前有 3 份健康干预方案正在生效
饮食、运动和监测方案已为您整理好，建议先查看本周重点。
查看方案
```

如果有近期指标数据，可轻量增强：

```text
近况分析
当前有 3 份健康干预方案正在生效
近期晚餐后血糖需要关注，建议先查看饮食方案和监测方案。
查看方案
```

如果无生效方案：

```text
近况分析
当前暂无生效中的干预方案
持续记录指标有助于服务团队了解您的情况。
记录指标
```

### 首页展示规则

1. 首页只展示摘要，不展开所有方案。
2. 近况分析卡最多展示 1 个主结论 + 1 句说明 + 1 个主按钮。
3. 主按钮优先跳转“干预方案列表”。
4. 若没有生效方案，主按钮跳转“指标录入”或“联系服务团队”，具体由是否已签约决定。
5. 不在这一阶段展示 AI 生成痕迹，避免用户以为已经进入 AI 健管师阶段。

## 5. 干预方案列表

### 页面目标

让患者看到自己当前正在执行哪些方案。

### 列表范围

第一阶段只展示“生效中”的方案，历史方案先不作为主路径。

后续可增加：

1. 生效中
2. 历史
3. 已失效

### 方案类型

列表需要支持以下类型：

| 方案类型 | 第一阶段是否展示 | 备注 |
| --- | --- | --- |
| 饮食方案 | 是 | 优先级最高 |
| 运动方案 | 是 | 优先级最高 |
| 监测方案 | 是 | 后续可转待办 |
| 随访计划 | 是 | 可先摘要展示 |
| 用药指导 | 预留 | 有数据则展示 |
| 健康周报 | 预留 | 有数据则展示 |
| 阶段性报告 | 预留 | 有数据则展示 |

### 列表卡片字段

每张方案卡建议展示：

| 字段 | 说明 |
| --- | --- |
| 方案类型 | 饮食方案、运动方案等 |
| 方案名称 | 管理端制定的名称 |
| 方案简述 | 一句话摘要 |
| 生效时间 | 方案生效时段 |
| 制定来源 | 服务团队制定 / AI 共创 / 智能推荐 |
| 制定人 | 医生或健管师，可选 |
| 查看入口 | 点击进入详情 |

### 排序建议

第一阶段按患者理解优先级排序：

1. 饮食方案
2. 运动方案
3. 监测方案
4. 随访计划
5. 用药指导
6. 健康周报
7. 阶段性报告

如果后端有管理端排序，则优先尊重后端排序。

## 6. 干预方案详情

### 页面目标

让患者能完整阅读单个方案。

### 详情页通用结构

```text
方案标题
方案状态 / 生效时间
方案简述
制定来源 / 制定人
核心内容
注意事项
```

### 三种内容形态兼容

| 内容形态 | C端展示方式 | 备注 |
| --- | --- | --- |
| 智能推荐老数据 | 按现有食谱/运动/监测结构展示 | 兼容历史数据 |
| 纯文本方案 | 标题 + 文本正文展示 | 兼容管理端人工文本 |
| AI 共创 JSON/HTML | 渲染结构化 HTML | 后续 AI 能力基础 |

### 第一阶段暂不做

1. 不做 AI 解读按钮的完整对话能力。
2. 不做“生成待办”按钮。
3. 不做动态追问。

但页面结构要预留入口位置，后续可以接：

```text
帮我解读这个方案
查看相关待办
```

## 7. 数据与接口边界

第一阶段建议 C 端需要一个“生效方案聚合接口”。

示例：

```text
GET /api/c/intervention-plans/active
```

返回内容建议：

```json
{
  "summary": {
    "activeCount": 3,
    "summaryText": "当前有 3 份健康干预方案正在生效",
    "suggestionText": "建议先查看本周饮食和监测重点"
  },
  "plans": [
    {
      "planId": "xxx",
      "planType": "diet",
      "planTypeName": "饮食方案",
      "title": "26年5月饮食方案",
      "summary": "本周重点控制晚餐主食和总热量",
      "status": "active",
      "effectiveTimeText": "2026.05.01-2026.05.31",
      "sourceType": "ai_json",
      "sourceText": "AI共创",
      "creatorName": "李时珍",
      "detailUrl": "/pages/plans/detail?id=xxx"
    }
  ]
}
```

详情接口：

```text
GET /api/c/intervention-plans/{planId}
```

详情需要返回：

1. 基础信息。
2. 内容形态：智能推荐 / 纯文本 / AI JSON HTML。
3. 可渲染内容。
4. 生效状态。
5. 后续关联待办预留字段。

## 8. 空状态

### 无生效方案

```text
当前暂无生效中的干预方案
多记录指标和饮食运动，有助于服务团队了解您的情况。
```

按钮：

1. 已签约：联系服务团队 / 记录指标。
2. 未签约：了解健康管理服务。

### 有方案但详情缺失

```text
方案内容正在整理中
服务团队完成后会同步到这里。
```

### 用户未实名

```text
完成实名认证后，可查看健康管理方案。
```

按钮：去认证。

## 9. 验收标准

第一阶段完成后，应满足：

1. 首页能展示近况分析卡。
2. 近况分析能准确显示当前生效方案数量。
3. 患者能从首页进入干预方案列表。
4. 干预方案列表能展示所有生效中方案。
5. 患者能进入每个方案详情。
6. 详情页能兼容智能推荐、纯文本、AI JSON/HTML 三种内容形态。
7. 无方案、未实名、未签约等状态有明确引导。
8. 页面结构为后续待办和 AI 解读预留入口。

## 10. 本阶段结论

第一阶段不追求把 AI、待办、动态表单一次做完。

最具体、最可落地的路径是：

```text
首页近况分析
→ 展示当前有几份生效中的干预方案
→ 引导患者进入方案列表
→ 患者查看各类方案详情
→ 为后续待办生成和 AI 解读预留入口
```

这一步完成后，C 端才真正具备承接管理端交付物的能力。
