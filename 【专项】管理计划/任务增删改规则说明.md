# 任务新增、编辑、删除规则说明

本文档用于说明 AI 健康管理计划工作流在处理待办任务时，如何判断新增任务、编辑任务和删除任务。

该规则面向 AI 决策节点和后续规则校验节点，不是前端页面操作说明。

## 一、总体原则

AI 的任务调整目标不是让任务数量越多越完整，而是让当前待办任务更符合患者本期健康管理重点、签约服务承诺和服务执行节奏。

AI 输出的任务调整结果应分为三类：

```json
{
  "task_adjustments": {
    "create_tasks": [],
    "modify_tasks": [],
    "delete_tasks": []
  }
}
```

通用要求：

1. 新增、编辑、删除必须分组输出。
2. 编辑任务和删除任务必须注明原任务 ID：`source_task_id`。
3. 新增任务没有原任务 ID，但必须说明任务主体、任务类型、执行人类型、计划履约时间和新增原因。
4. 同一个原任务 ID 只能出现在一个操作分组中。
5. 如果一个任务可以通过编辑继续服务于当前管理目标，应优先编辑，不应新增重复任务。
6. AI 只输出建议结果，最终是否落库应由规则校验节点和业务系统确认。
7. 给代码节点读取的枚举值使用短码，例如 `1`、`2`、`3`，不使用长英文短语。

编码要求：

- `template_code` 表示任务模板编号，由代码节点映射为默认动作集。
- `edit_type` 表示编辑类型编号，由代码节点映射为编辑策略。
- `reason_code` 表示原因编号，由代码节点用于分类、统计和规则判断。
- `followup_type_code`、`indicator_code`、`notice_template_code` 等由代码节点读取的值，也优先使用短码。
- 给管理者展示的原因使用 `reason_text`，由 AI 根据实际情况生成一句自然语言说明。

## 二、任务类型基础规则

| 任务类型 | 编码 | 支持的执行人类型 | 关联随访表单 | 关联指标 | C 端跳转链接 | 患者消息提醒 |
| --- | --- | --- | --- | --- | --- | --- |
| 常规 | `normal` | 服务团队、患者本人 | 不支持 | 不支持 | 支持，仅执行人为患者本人时使用 | 支持 |
| 随访 | `followup` | 服务团队 | 支持 | 不支持 | 不支持 | 支持 |
| 指标监测 | `indicator_monitoring` | 患者本人 | 不支持 | 支持 | 支持 | 支持 |

AI 不能输出违反任务类型规则的调整结果。

示例：

- `followup` 任务不能指定执行人为患者本人。
- `indicator_monitoring` 任务不能指定执行人为服务团队。
- `normal` 任务不能关联随访表单或指标。
- `followup` 任务不能配置 C 端跳转链接。

## 三、新增任务规则

### 3.1 允许新增的前置条件

只有满足以下情况之一时，才允许新增任务：

1. 管理画像中存在关键干预事项，但当前待办任务没有覆盖。
2. 签约产品或服务包承诺了某类管理动作，但当前待办任务缺失。
3. 当前相关任务长期逾期且不适合继续保留，需要重新建立服务节奏。
4. 当前任务只覆盖提醒动作，但缺少必要的随访、指标监测或患者自我管理动作。
5. 当前任务执行人类型错误，且无法通过编辑原任务解决。

### 3.2 不允许新增的情况

以下情况不应新增任务：

1. 已有待办任务可以通过编辑覆盖相同任务主体。
2. 只是为了让任务说明更完整，但不构成新的管理动作。
3. 管理画像中只是低优先级关注点，不需要在本期形成任务。
4. 新增任务计划履约时间超过签约有效期。
5. 同一任务主体已经存在未完成任务，且该任务仍在合理执行窗口内。
6. 新增后会造成任务过密或明显超出服务团队执行能力。

### 3.3 新增任务必填字段

新增任务建议输出以下字段：

```json
{
  "template_code": "1",
  "task_type": "normal",
  "contract_product_id": "CONTRACT-PRODUCT-001",
  "contract_product_name": "糖尿病慢病管理服务包",
  "reference_task_id": "TASK-20260613-002",
  "executor_type": "service_team",
  "planned_time": "2026-06-20 10:00:00",
  "valid_days": 7,
  "priority": "medium",
  "reason_code": "1",
  "reason_text": "患者本期需要关注用药依从性，但当前待办任务中缺少可承接该管理动作的有效任务。"
}
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `template_code` | 任务模板编号，表示新增哪一类任务。代码节点根据该编号读取默认动作集。 |
| `task_type` | 任务类型，取值为 `normal`、`followup`、`indicator_monitoring`。 |
| `contract_product_id` | 签约产品 ID，用于证明任务归属于哪个服务包。 |
| `contract_product_name` | 签约产品名称，也就是服务包名称。 |
| `reference_task_id` | 参考任务 ID。代码节点可从该任务复制执行团队、执行人、签约产品等信息。 |
| `executor_type` | 执行人类型，取值为 `service_team` 或 `patient`。 |
| `planned_time` | 计划履约时间。 |
| `valid_days` | 任务有效期天数。 |
| `priority` | 任务优先级，取值为 `high`、`medium`、`low`。 |
| `reason_code` | 新增原因编号。 |
| `reason_text` | 面向管理者展示的新增原因。 |

任务模板编号建议：

| 编号 | 默认动作集 |
| --- | --- |
| `1` | 用药依从性提醒 |
| `2` | GLP-1 注射提醒 |
| `3` | 空腹血糖监测 |
| `4` | 血压监测 |
| `5` | 高血压随访 |
| `6` | 复诊提醒 |

### 3.4 不同任务类型的新增补充字段

原则上，随访表单、指标、通知模板、C 端跳转链接等字段应由代码节点根据 `template_code` 从默认动作集中补齐，不要求 AI 每次输出。

只有在需要覆盖默认动作集时，AI 才输出短码形式的覆盖字段。

随访任务如需覆盖默认配置，可补充：

```json
{
  "followup_type_code": "1",
  "followup_form_id": "FORM-HBP-FOLLOWUP-001",
  "followup_form_name": "高血压随访问卷"
}
```

指标监测任务如需覆盖默认配置，可补充：

```json
{
  "indicator_code": "1",
  "indicator_name": "空腹血糖"
}
```

患者本人执行且需要覆盖小程序触达配置时，可补充：

```json
{
  "patient_notice": {
    "enabled": true,
    "notice_template_code": "1"
  },
  "client_jump": {
    "enabled": true,
    "jump_code": "1"
  }
}
```

补充字段编号建议：

| 字段 | 编号 | 含义 |
| --- | --- | --- |
| `followup_type_code` | `1` | 高血压随访 |
| `followup_type_code` | `2` | 糖尿病随访 |
| `indicator_code` | `1` | 空腹血糖 |
| `indicator_code` | `2` | 血压 |
| `indicator_code` | `3` | BMI |
| `notice_template_code` | `1` | 指标上传提醒 |
| `notice_template_code` | `2` | 用药提醒 |
| `jump_code` | `1` | 指标上传页 |
| `jump_code` | `2` | 随访填写页 |

### 3.5 新增任务数量控制

建议规则：

1. 单次 AI 调整最多新增 3 个任务。
2. 同一 `template_code` 最多新增 1 个任务。
3. 高优先级事项优先新增。
4. 低优先级事项默认进入管理画像，不默认新增任务。
5. 如果新增任务是替代长期逾期任务，需要在原因中说明替代关系。

## 四、编辑任务规则

### 4.1 允许编辑的前置条件

满足以下情况之一时，可以编辑任务：

1. 原任务方向基本正确，但任务名称或说明不够明确。
2. 原任务仍符合当前管理目标，但计划履约时间不合理。
3. 原任务执行人缺失或执行人类型可以调整后继续执行。
4. 原任务和患者管理画像相关，但需要补充更清晰的任务主体。
5. 原任务可以覆盖某个缺失管理动作，因此通过编辑替代新增。

### 4.2 不建议编辑的情况

以下情况不应优先编辑：

1. 原任务长期逾期，且继续保留会影响整体服务节奏。
2. 原任务主题和当前患者管理画像无关。
3. 原任务来源于错误服务包，无法证明和当前签约服务有关。
4. 原任务类型错误，且受系统能力限制无法通过编辑变更为合法任务。
5. 原任务已经被判定为必须删除。

### 4.3 编辑任务必填字段

编辑任务必须输出原任务 ID：

```json
{
  "source_task_id": "TASK-20260613-001",
  "edit_type": "1",
  "patch": {
    "task_name": "GLP-1注射提醒",
    "description": "提醒患者按计划完成本周GLP-1注射，并确认是否出现不适。",
    "planned_time": "2026-06-15 10:00:00",
    "priority": "medium"
  },
  "reason_code": "1",
  "reason_text": "原任务只提示注射时间，说明不够具体，建议补充注射执行确认和不适反馈内容。"
}
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `source_task_id` | 被编辑的原任务 ID。 |
| `edit_type` | 编辑类型编号。代码节点根据编号判断本次编辑策略。 |
| `patch` | 只放需要修改的字段，不需要重复输出未变化字段。 |
| `reason_code` | 编辑原因编号。 |
| `reason_text` | 面向管理者展示的编辑原因。 |

编辑类型编号建议：

| 编号 | 编辑类型 |
| --- | --- |
| `1` | 调整时间并优化任务说明 |
| `2` | 仅调整计划履约时间 |
| `3` | 补充或调整执行人 |
| `4` | 调整患者通知配置 |
| `5` | 调整优先级 |

### 4.4 可编辑字段范围

AI 可以建议编辑以下字段：

```text
task_name
description
priority
planned_time
valid_days
executor_type
service_team_id
service_team_name
planned_executor_id
planned_executor_name
patient_notice.enabled
patient_notice.notice_template_code
client_jump.enabled
client_jump.jump_code
```

条件性可编辑字段：

```text
followup_type_code
followup_form_id
followup_form_name
indicator_code
indicator_name
```

条件说明：

- 只有随访任务可以编辑随访相关字段。
- 只有指标监测任务可以编辑指标相关字段。
- 只有规则允许 C 端跳转的任务可以编辑跳转链接。

### 4.5 不建议 AI 编辑的字段

以下字段不建议由 AI 编辑：

```text
task_id
task_source
source_rule_id
status
contract_product_id
contract_product_name
```

说明：

- `task_id` 是原任务标识，不允许变更。
- `task_source` 和 `source_rule_id` 涉及任务来源追溯，不应由 AI 改写。
- `status` 应由业务系统流转，不应由 AI 直接修改。
- `contract_product_id` 和 `contract_product_name` 用于证明任务归属服务包，不建议 AI 自行改动；如确需变更，应进入人工确认。

## 五、删除任务规则

### 5.1 允许删除的前置条件

满足以下情况之一时，可以建议删除任务：

1. 任务长期逾期，继续保留会造成服务节奏堆积。
2. 任务目的过于模糊，无法通过编辑形成明确管理动作。
3. 任务与当前患者管理画像无关。
4. 任务与其他待办任务重复，且已有更合适任务覆盖相同任务主体。
5. 任务来源或签约产品不匹配当前服务周期。
6. 任务类型、执行人类型和系统规则冲突，且无法通过编辑修正。

### 5.2 不允许删除的情况

以下情况不应删除，除非有人工确认：

1. 当前存在 `task_source = stratified_management` 的任务时，最终至少保留 1 个分层管理来源任务。
2. 当前存在 `task_source = target_management` 的任务时，最终至少保留 1 个分标管理来源任务。
3. 任务来源于当前有效签约服务包，且属于服务承诺必须执行动作。
4. 高优先级任务仍在有效执行窗口内。
5. 删除后该任务主体没有其他任务覆盖，且该主体属于当前关键管理动作。

### 5.3 删除任务必填字段

删除任务必须输出原任务 ID：

```json
{
  "source_task_id": "TASK-20260613-004",
  "reason_code": "1",
  "reason_text": "该任务已逾期28天且内容较泛，继续保留会干扰本期更具体的管理任务安排。"
}
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `source_task_id` | 被删除的原任务 ID。 |
| `reason_code` | 删除原因编号。 |
| `reason_text` | 面向管理者展示的删除原因。 |

删除任务不应输出 `patch`，也不应输出新的任务内容。

## 六、原因编号建议

### 6.1 新增原因编号

| 编号 | 含义 |
| --- | --- |
| `1` | 缺少关键管理动作。 |
| `2` | 缺少签约服务承诺动作。 |
| `3` | 替代长期逾期且不适合继续保留的任务。 |
| `4` | 缺少患者自我管理动作。 |
| `5` | 缺少必要指标监测动作。 |
| `6` | 缺少必要随访动作。 |

### 6.2 编辑原因编号

| 编号 | 含义 |
| --- | --- |
| `1` | 原任务目的不明确，需要调整名称或说明。 |
| `2` | 原计划履约时间不合理，需要重排。 |
| `3` | 原任务缺少明确执行人。 |
| `4` | 原任务执行人类型不符合任务类型规则。 |
| `5` | 原任务需要对齐当前管理重点。 |
| `6` | 通过编辑已有任务覆盖管理动作，避免重复新增。 |

### 6.3 删除原因编号

| 编号 | 含义 |
| --- | --- |
| `1` | 长期逾期，继续保留会影响服务节奏。 |
| `2` | 与其他任务主体重复，且已有更合适任务覆盖。 |
| `3` | 与当前管理画像无关。 |
| `4` | 无法通过编辑修复。 |
| `5` | 与当前签约产品或服务包不匹配。 |
| `6` | 任务类型规则冲突，无法合法执行。 |

## 七、推荐输出结构

AI 工作流建议输出“决策版”结果，避免输出长篇自然语言：

```json
{
  "task_adjustments": {
    "create_tasks": [
      {
        "template_code": "1",
        "task_type": "normal",
        "contract_product_id": "CONTRACT-PRODUCT-001",
        "contract_product_name": "糖尿病慢病管理服务包",
        "reference_task_id": "TASK-20260613-002",
        "executor_type": "service_team",
        "planned_time": "2026-06-20 10:00:00",
        "valid_days": 7,
        "priority": "medium",
        "reason_code": "1",
        "reason_text": "患者本期需要关注用药依从性，但当前待办任务中缺少可承接该管理动作的有效任务。"
      }
    ],
    "modify_tasks": [
      {
        "source_task_id": "TASK-20260613-001",
        "edit_type": "1",
        "patch": {
          "task_name": "GLP-1注射提醒",
          "description": "提醒患者按计划完成本周GLP-1注射，并确认是否出现不适。",
          "planned_time": "2026-06-15 10:00:00"
        },
        "reason_code": "1",
        "reason_text": "原任务只提示注射时间，说明不够具体，建议补充注射执行确认和不适反馈内容。"
      }
    ],
    "delete_tasks": [
      {
        "source_task_id": "TASK-20260613-004",
        "reason_code": "1",
        "reason_text": "该任务已逾期28天且内容较泛，继续保留会干扰本期更具体的管理任务安排。"
      }
    ]
  }
}
```

## 八、规则校验节点建议

AI 输出后，建议由规则节点做以下校验：

1. `create_tasks`、`modify_tasks`、`delete_tasks` 是否分组存在。
2. `modify_tasks` 和 `delete_tasks` 是否都包含 `source_task_id`。
3. 同一个 `source_task_id` 是否只出现一次。
4. 新增任务数量是否超过上限。
5. 新增任务是否违反任务类型和执行人类型规则。
6. 新增任务计划履约时间是否超过签约有效期。
7. 当前存在分层管理任务时，最终是否至少保留 1 个。
8. 当前存在分标管理任务时，最终是否至少保留 1 个。
9. 新增任务模板是否已被现有保留任务或编辑任务覆盖。
10. 删除任务后是否导致关键管理动作完全缺失。

规则节点校验不通过时，不应直接落库，应返回 AI 重新修正或进入人工确认。
