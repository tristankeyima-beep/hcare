# 任务调整指令解析与校验规则

本文档用于说明 AI 工作流中第 4 步“指令解析代码节点”和第 5 步“规则校验代码节点”的处理逻辑。

它不负责说明 LLM 如何判断增、删、改，而是说明 LLM 输出任务调整指令后，代码节点如何解析、补齐字段和校验结果。

## 一、输入与输出

### 输入

代码节点接收第 3 步 LLM 输出的任务调整指令：

```json
{
  "task_change_instructions": {
    "create": [],
    "edit": [],
    "delete": []
  }
}
```

同时代码节点还需要读取：

- 原始待办任务列表
- 数据处理后的标准任务数据
- 签约服务和签约产品信息
- 默认动作集
- 任务类型规则
- 当前时间和签约有效期

### 输出

代码节点输出正式任务调整方案：

```json
{
  "task_adjustments": {
    "create_tasks": [],
    "modify_tasks": [],
    "delete_tasks": []
  }
}
```

## 二、指令结构要求

### 2.1 新增指令

新增指令用于告诉代码节点“新增哪类任务，以及本次任务的关键覆盖信息”。

```json
{
  "template_code": "3",
  "reference_task_id": "TASK-001",
  "planned_time": "2026-06-16 08:00:00",
  "instruction_note": "提醒患者在早餐前完成空腹血糖测量并上传记录。",
  "reason_text": "患者本期需要关注血糖控制，但当前待办任务中缺少可承接空腹血糖监测的有效任务。"
}
```

字段要求：

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| `template_code` | 必填 | 默认动作集编号。 |
| `reference_task_id` | 建议填 | 参考任务 ID，用于复制执行团队、执行人、签约产品等信息。 |
| `planned_time` | 必填 | 计划完成时间。 |
| `instruction_note` | 必填 | 本次任务说明重点。 |
| `reason_text` | 必填 | 给管理者看的自然语言原因。 |

### 2.2 编辑指令

编辑指令用于告诉代码节点“编辑哪条原任务，以及只修改哪些字段”。

```json
{
  "task_id": "TASK-001",
  "patch": {
    "planned_time": "2026-06-15 10:00:00",
    "description": "提醒患者按计划完成本周GLP-1注射，并确认是否出现不适。"
  },
  "reason_text": "原任务已逾期且说明较简单，建议调整履约时间并补充注射执行确认内容。"
}
```

字段要求：

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| `task_id` | 必填 | 被编辑的原任务 ID。 |
| `patch` | 必填 | 只包含需要修改的字段。 |
| `reason_text` | 必填 | 给管理者看的自然语言原因。 |

### 2.3 删除指令

删除指令用于告诉代码节点“删除哪条原任务，以及删除原因”。

```json
{
  "task_id": "TASK-004",
  "reason_text": "该任务已逾期28天且内容较泛，继续保留会干扰本期更具体的管理任务安排。"
}
```

字段要求：

| 字段 | 要求 | 说明 |
| --- | --- | --- |
| `task_id` | 必填 | 被删除的原任务 ID。 |
| `reason_text` | 必填 | 给管理者看的自然语言原因。 |

删除指令不允许包含 `patch`、`planned_time`、`template_code` 或 `instruction_note`。

## 三、指令解析规则

### 3.1 解析新增指令

代码节点处理新增指令时：

1. 根据 `template_code` 读取默认动作集。
2. 根据 `reference_task_id` 查找参考任务。
3. 从参考任务中复制可复用字段，例如执行团队、计划执行人、签约产品。
4. 如果 `reference_task_id` 为空或不可用，则从签约服务中补齐服务团队和主责健管师。
5. 使用 `planned_time` 覆盖默认计划时间。
6. 使用 `instruction_note` 生成或覆盖任务说明。
7. 保留 `reason_text`，用于展示和审计。

新增任务中不应由 LLM 直接生成的字段，优先由默认动作集或业务系统补齐。

### 3.2 解析编辑指令

代码节点处理编辑指令时：

1. 根据 `task_id` 查找原任务。
2. 复制原任务完整字段。
3. 校验 `patch` 中的字段是否允许编辑。校验方式是将 `patch` 中出现的字段名，与允许编辑字段白名单做比对；如果存在白名单之外的字段，则校验不通过。
4. 只应用 `patch` 中出现的字段。
5. 保留原任务 ID、任务来源、来源规则、签约产品等不可变字段。
6. 保留 `reason_text`，用于展示和审计。

### 3.3 解析删除指令

代码节点处理删除指令时：

1. 根据 `task_id` 查找原任务。
2. 校验该任务是否允许删除。
3. 生成删除候选。
4. 保留 `reason_text`，用于展示和审计。

## 四、核心字段规则

本工作流不做泛化的任务字段编辑。新增和编辑只允许围绕少量核心字段产生指令，其余字段由默认动作集、原任务、参考任务或签约服务补齐。

### 4.1 新增指令核心字段

新增指令只关注以下字段：

| 字段 | 作用 |
| --- | --- |
| `template_code` | 说明新增哪一类任务。 |
| `reference_task_id` | 说明执行团队、执行人、签约产品等字段优先参考哪条现有任务。 |
| `planned_time` | 说明新增任务的计划完成时间。 |
| `instruction_note` | 说明本次任务的执行重点，可用于生成任务说明。 |
| `reason_text` | 说明为什么新增，给管理者查看。 |

新增任务的任务名称、任务类型、执行人类型、有效期、优先级、随访表单、关联指标、患者通知、跳转入口等字段，不要求 LLM 输出，由代码节点根据 `template_code` 从默认动作集中补齐。

### 4.2 编辑指令核心字段

编辑指令只关注以下字段：

| 字段 | 作用 |
| --- | --- |
| `task_id` | 说明编辑哪条原任务。 |
| `patch` | 说明本次具体修改哪些字段。 |
| `reason_text` | 说明为什么编辑，给管理者查看。 |

`patch` 只允许包含以下字段：

```text
planned_time
valid_days
task_name
description
```

白名单校验示例：

```text
允许字段 = [planned_time, valid_days, task_name, description]
patch字段 = Object.keys(patch)
非法字段 = patch字段 - 允许字段

如果非法字段不为空，则校验不通过。
```

字段含义：

- `planned_time`：调整计划完成时间。
- `valid_days`：调整任务有效期。
- `task_name`：在原名称过于模糊时，调整任务名称。
- `description`：补充或重写任务说明。

如果后续确认患者通知内容也需要由 AI 调整，再单独扩展 `patient_notice.reminder_content` 和 `patient_notice.prompt_description`，不要默认开放。

### 4.3 不允许由 LLM 覆盖的字段

以下字段不允许由 LLM 指令直接覆盖：

```text
task_id
task_source
source_rule_id
status
contract_product_id
contract_product_name
service_team_id
service_team_name
executor_type
planned_executor_id
planned_executor_name
priority
patient_notice.enabled
client_jump.jump_code
followup_type_code
followup_form_id
indicator_code
```

说明：

- 任务 ID、任务来源、来源规则用于追溯，不允许改写。
- 签约产品和服务团队应从原任务、参考任务或签约服务中补齐。
- 执行人类型受任务类型规则约束，不由 LLM 自由变更。
- 随访表单、关联指标、患者通知和跳转入口由默认动作集或业务系统补齐，不作为本阶段 LLM 编辑重点。

## 五、规则校验

规则校验节点只围绕本工作流允许的核心字段做校验，不做泛化字段校验。

### 5.1 基础结构校验

1. `create`、`edit`、`delete` 是否为数组。
2. 新增指令是否包含 `template_code`、`planned_time`、`instruction_note`、`reason_text`。
3. 编辑指令是否包含 `task_id`、`patch`、`reason_text`。
4. 删除指令是否包含 `task_id`、`reason_text`。
5. 同一个 `task_id` 是否被重复编辑或删除。
6. 同一个 `task_id` 是否同时出现在编辑和删除中。

### 5.2 新增指令校验

1. `template_code` 是否存在于默认动作集中。
2. `planned_time` 是否为空、格式是否正确。
3. `planned_time` 是否早于当前时间。
4. `planned_time` 是否超过签约有效期。
5. `instruction_note` 是否为空。
6. `reason_text` 是否为空。
7. `reference_task_id` 如果存在，是否能在原始待办任务中找到。
8. 新增任务数量是否超过上限。
9. 同一 `template_code` 是否重复新增。
10. 新增任务是否已被保留任务或编辑后任务覆盖。

### 5.3 编辑指令校验

1. `task_id` 是否存在于原始待办任务列表。
2. `patch` 是否为空。
3. `patch` 是否只包含 `planned_time`、`valid_days`、`task_name`、`description`。
4. 如果 `patch.planned_time` 存在，时间格式是否正确，且不早于当前时间、不超过签约有效期。
5. 如果 `patch.valid_days` 存在，是否为正整数。
6. 如果 `patch.task_name` 存在，是否为空。
7. 如果 `patch.description` 存在，是否为空。
8. `reason_text` 是否为空。

### 5.4 删除指令校验

1. `task_id` 是否存在于原始待办任务列表。
2. 删除指令是否只包含 `task_id`、`reason_text`。
3. `reason_text` 是否为空。
4. 当前存在分层管理来源任务时，最终是否至少保留 1 个。
5. 当前存在分标管理来源任务时，最终是否至少保留 1 个。
6. 删除任务是否属于当前签约服务承诺的必须执行动作。
7. 删除后是否导致管理画像中的关键动作完全缺失。

## 六、校验失败处理

校验失败时，不应直接落库。

处理方式：

1. 如果是核心字段缺失、短码不存在、重复操作等结构问题，返回指令修正。
2. 如果是删除保护、签约有效期、服务承诺动作缺失等业务风险，进入人工确认。
3. 如果是新增任务与已有任务重复，优先转为编辑原任务。
4. 如果 `patch` 包含非核心字段，移除非法字段或进入人工确认。

## 七、关键原则

- LLM 输出的是调整指令，不是最终任务对象。
- 新增任务由默认动作集补齐大部分字段。
- 编辑任务只应用 `patch`，不重建任务。
- 删除任务只基于原任务 ID 生成删除候选。
- 代码节点负责解析、补字段和校验。
- 规则校验通过后，才输出最终任务调整方案。

## 八、可选扩展

如果后续需要做原因统计或质检分类，可以在新增、编辑、删除指令中增加 `reason_code`。

该字段不作为当前主流程必填项。管理者理解原因时，以 `reason_text` 为准。
