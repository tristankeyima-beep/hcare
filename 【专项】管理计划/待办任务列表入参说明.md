# 待办任务列表入参说明

本文档用于模拟 AI 健康管理计划工作流的入参：`待办任务列表`。

该入参只承载患者当前仍需要处理的任务，供 AI 判断哪些任务应保留、修改、删除，以及是否需要补充新的管理任务。它不是页面详情字段的简单搬运，而是面向 AI 决策整理后的任务数据。

## 一、入参名称

```json
{
  "pending_task_list": []
}
```

中文名称：待办任务列表

业务含义：当前患者在签约服务周期内尚未完成、仍可能影响健康管理服务节奏的任务集合。

## 三、字段说明

| 字段 | 类型 | 是否建议必传 | 含义 | AI 使用方式 |
| --- | --- | --- | --- | --- |
| `pending_task_list` | array | 是 | 待办任务列表。 | AI 只基于该列表判断当前未完成任务的调整方案。 |
| `task_id` | string | 是 | 原任务唯一 ID。 | 修改和删除任务时必须回传该 ID。 |
| `task_type` | string | 是 | 任务类型。可选值：`normal` 常规、`followup` 随访、`indicator_monitoring` 指标监测。 | 决定任务能否关联随访表单、指标、C 端跳转和执行人类型。 |
| `followup_type_code` | string | 条件必传 | 随访类型编号。仅当 `task_type = followup` 时传入，例如 `1` 表示高血压随访。 | 帮助 AI 判断随访任务是否匹配患者管理病种。 |
| `task_source` | string | 是 | 任务来源。建议可选值：`manual` 手动创建、`stratified_management` 分层管理、`target_management` 分标管理、`service_plan` 签约服务计划。 | 用于执行保留规则，例如已有分层管理任务时至少保留 1 个。 |
| `source_name` | string | 是 | 任务来源中文名称。 | 便于 AI 理解来源语义，也便于最终展示。 |
| `source_rule_id` | string | 否 | 来源规则 ID。分层、分标、服务计划等系统规则生成的任务建议传入。 | 用于判断任务是否来自系统规则，降低误删风险。 |
| `status` | string | 是 | 任务状态。当前入参一般只传 `pending`。 | AI 需要确认该任务仍未完成。 |
| `is_overdue` | boolean | 是 | 是否已逾期。 | 判断是否存在任务堆积、服务节奏失衡。 |
| `overdue_days` | number | 是 | 已逾期天数。未逾期时为 0。 | 长时间逾期任务可能进入删除或重排判断。 |
| `task_name` | string | 是 | 任务名称。 | 判断任务主题、是否目的明确、是否与其他任务重复。 |
| `description` | string | 建议传 | 任务说明。 | 判断任务目的、执行方式、是否可以通过修改继续复用。 |
| `priority` | string | 是 | 优先级。可选值：`high`、`medium`、`low`。 | 辅助判断调整优先级，但不应单独决定删除。 |
| `planned_time` | string | 是 | 计划履约时间。 | 判断任务是否逾期、是否需要重排、是否超出签约有效期。 |
| `valid_days` | number | 是 | 任务有效期天数。 | 判断任务窗口是否合理。 |
| `remaining_days` | number | 是 | 剩余有效天数。已逾期时建议传 0。 | 减少 AI 自行计算日期带来的错误。 |
| `executor.executor_type` | string | 是 | 执行人类型。可选值：`service_team` 服务团队、`patient` 患者本人。 | 校验任务类型和执行人是否匹配。 |
| `executor.contract_product_id` | string | 建议传 | 签约产品 ID，也可以理解为患者购买或签约的服务包 ID。 | 证明任务来自哪个签约服务包，辅助判断任务是否应保留或是否属于服务承诺动作。 |
| `executor.contract_product_name` | string | 建议传 | 签约产品名称，也可以理解为服务包名称。 | 帮助 AI 理解任务和签约服务之间的关系。 |
| `executor.service_team_id` | string/null | 条件必传 | 服务团队 ID。执行人类型为服务团队时传入。 | 生成或修改服务团队执行任务时使用。 |
| `executor.service_team_name` | string/null | 条件必传 | 服务团队名称。 | 帮助 AI 理解当前服务承接方。 |
| `executor.planned_executor_id` | string/null | 否 | 计划执行人 ID。 | 判断是否缺失明确执行人。 |
| `executor.planned_executor_name` | string/null | 否 | 计划执行人姓名。 | 判断任务是否有明确责任人。 |
| `followup_form.enabled` | boolean | 条件必传 | 是否关联随访表单。仅随访任务使用。 | 判断随访任务是否有执行载体。 |
| `followup_form.form_id` | string | 条件必传 | 随访表单 ID。 | 修改随访任务时保留或调整表单关联。 |
| `followup_form.form_name` | string | 条件必传 | 随访表单名称。 | 辅助 AI 理解随访内容。 |
| `indicator.enabled` | boolean | 条件必传 | 是否关联指标。仅指标监测任务使用。 | 判断指标监测任务是否完整。 |
| `indicator.indicator_code` | string | 条件必传 | 指标编号，例如 `1` 表示空腹血糖。 | 判断监测指标是否与患者管理画像匹配。 |
| `indicator.indicator_name` | string | 条件必传 | 指标名称。 | 辅助 AI 理解监测内容。 |
| `attachments.image_count` | number | 否 | 图片数量。 | 一般只作为补充信息，不建议默认传图片内容给 AI。 |
| `client_jump.enabled` | boolean | 是 | 是否配置 C 端跳转地址。 | 判断患者本人执行任务是否有入口。 |
| `client_jump.jump_code` | string/null | 条件必传 | C 端跳转入口编号，例如 `1` 表示指标上传页。 | 仅在任务类型和执行人规则允许时使用，具体 URL 由代码节点映射。 |
| `patient_notice.enabled` | boolean | 是 | 是否给患者发送小程序服务通知。 | 判断任务是否涉及患者触达。 |
| `patient_notice.reminder_content` | string/null | 否 | 提醒内容。 | 可用于理解患者收到的短提醒，不建议让 AI 每次重写。 |
| `patient_notice.prompt_description` | string/null | 否 | 提示说明。 | 可作为患者侧补充说明。 |

## 四、任务类型约束

这些约束建议由工作流规则节点校验，不建议完全交给 AI 自由判断。

| 任务类型 | 支持的执行人类型 | 是否支持关联随访表单 | 是否支持关联指标 | 是否支持 C 端跳转链接 | 是否支持患者消息提醒 |
| --- | --- | --- | --- | --- | --- |
| `normal` 常规 | 服务团队、患者本人 | 不支持 | 不支持 | 支持，仅执行人为患者本人时使用 | 支持 |
| `followup` 随访 | 服务团队 | 支持 | 不支持 | 不支持 | 支持 |
| `indicator_monitoring` 指标监测 | 患者本人 | 不支持 | 支持 | 支持 | 支持 |

## 六、给 AI 的使用说明建议

AI 不应直接基于任务名称做增删改判断，应综合任务来源、任务类型、执行人、计划时间、逾期情况和患者管理画像判断。

修改任务和删除任务时，必须回传原任务 ID：`task_id`。

新增任务时，不需要原任务 ID，但必须说明新增任务主体、任务类型、执行人类型、计划履约时间和新增原因。

已有 `task_source = stratified_management` 的任务时，最终方案至少保留 1 个分层管理来源任务。

已有 `task_source = target_management` 的任务时，最终方案至少保留 1 个分标管理来源任务。

长期逾期、目的模糊、缺少明确责任人的任务，可以进入修改或删除候选，但删除前必须确认它不是必须保留的分层管理或分标管理任务。
