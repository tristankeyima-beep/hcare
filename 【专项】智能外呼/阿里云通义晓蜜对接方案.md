# 阿里云通义晓蜜对接方案

## 1. 一期定位与范围

### 1.1 目标

将阿里云通义晓蜜智能外呼接入慢病管理系统（以下简称“慢管”），以糖尿病患者健康随访为首个场景，跑通：

```text
慢管配置随访场景
→ 慢管创建 / 批量发起电话随访
→ 阿里云执行语音外呼
→ 慢管同步通话结果
→ 健管师查看结果并按需 AI 提炼
→ 随访结论进入后续 PDCA
```

### 1.2 一期边界

- 阿里云负责：大模型场景、话术、变量、标签、FAQ、语音能力、外呼调度与重拨。
- 慢管负责：场景关联配置、外呼批次和患者任务管理、发起接口调用、结果同步、结果展示、健管师 AI 提炼和 PDCA 使用。
- 不做慢管与阿里云的场景双向同步；场景内容只在阿里云控制台配置和发布。
- 首个固定场景为“糖尿病患者健康随访”，时长目标 2—3 分钟。
- 一期覆盖拒访、忙碌、非本人、风险症状、人工跟进、方言、打断和 FAQ 命中等场景能力验证。

## 2. 核心数据模型

### 2.1 已确认的对应关系

```text
1 个慢管外呼批次
= 1 个阿里 JobGroup
= N 个患者随访任务（即 N 个阿里 Job）
= 每个 Job 有 0~N 次实际通话 Task
```

示例：

```text
糖尿病日常随访批次（100 人）
└─ 阿里 JobGroup: job_group_001
   ├─ 患者 A：慢管随访任务 task_A → 阿里 Job job_A
   │  ├─ Task task_A_01：无人接听
   │  └─ Task task_A_02：接通并完成
   ├─ 患者 B：慢管随访任务 task_B → 阿里 Job job_B
   └─ ……
```

同一个 `JobGroup` 内的患者必须使用同一套场景、主叫号码和外呼策略。不同病种场景、不同 `ScriptId`、不同外呼策略或不同主叫号码时，需要拆分为不同外呼批次。

### 2.2 慢管建议保存的实体

| 实体 | 主要字段 | 说明 |
| --- | --- | --- |
| AI 随访场景配置 | 随访类型、`InstanceId`、`ScriptId`、主叫号码、外呼策略、变量定义、标签定义 | 慢管与阿里云的静态关联配置 |
| 外呼批次 | 批次名称、场景配置快照、`JobGroupId`、总人数、批次发起时间 | 对应一个阿里 `JobGroup` |
| AI 随访外呼记录 | 患者 ID、慢管随访任务 ID、`referenceId`、`JobId`、外呼状态、随访结果状态 | 对应一个患者的阿里 `Job` |
| 通话尝试记录 | `TaskId`、`CallId`、通话状态、时间、时长、结束原因、录音信息 | 对应一次实际拨打 |
| 随访结果 | 原始标签、对话文本、结构化结果、AI 提炼结果 | 用于详情展示与 PDCA |

## 3. ID 与字段对应关系

### 3.1 场景配置期

| ID / 字段 | 产生方式 | 慢管用途 |
| --- | --- | --- |
| `InstanceId` | 阿里云创建智能外呼业务实例后生成 | 指定接入哪个阿里云外呼实例；调用接口时必传 |
| `ScriptId` | 在该实例中创建并发布糖尿病 / 高血压等场景后生成 | 随访类型关联的核心 ID；创建 `JobGroup` 时决定使用哪个外呼场景 |
| `CallingNumber` | 阿里云号码资源绑定到实例后获得 | 指定患者看到的主叫号码；一期建议明确配置，不使用默认全部号码 |
| 外呼策略 | 慢管配置模板，发起时展开为 `StrategyJson` / `RecallStrategyJson` | 重拨次数、间隔、可外呼时间段等由阿里云执行 |

慢管应维护如下映射：

| 慢管随访类型 | InstanceId | ScriptId | 主叫号码 | 外呼策略 |
| --- | --- | --- | --- | --- |
| `DIABETES_HEALTH_FOLLOWUP` | 慢病外呼业务实例 | 糖尿病患者健康随访场景 | 已绑定号码 | 糖尿病日常随访策略 |
| `HYPERTENSION_HEALTH_FOLLOWUP` | 慢病外呼业务实例 | 高血压患者健康随访场景 | 已绑定号码 | 高血压日常随访策略 |

`ScriptId` 是业务上“慢管随访类型关联的阿里云 ID”；`InstanceId + ScriptId` 共同构成完整的场景接入配置。

> 注意：阿里云创建任务组的入参叫 `ScriptId`，部分返回结构中展示为 `ScenarioId`。一期配置保存 `ScriptId`，运行记录同时保存阿里云返回的 `ScenarioId`，用于排障核验。

### 3.2 每次外呼运行期

| ID / 字段 | 产生方式 | 慢管用途 |
| --- | --- | --- |
| `referenceId` | 慢管在创建本次患者随访任务时自行生成 | 跨系统稳定关联键；建议值为慢管本次随访任务 ID，而不是患者 ID |
| `JobGroupId` | `CreateJobGroup` 成功后阿里云返回 | 外呼批次主键；用于批次下发和状态查询 |
| `JobId` / `JobsId[]` | `AssignJobs` 成功后阿里云返回 | 患者 AI 随访外呼记录主键；用于获取完整详情 |
| `TaskId` | 实际通话产生后，在任务详情中返回 | 一次实际通话 ID；用于查询单次通话和下载录音 |
| `CallId` | 阿里云 SIP 呼叫产生 | 技术排障与对账留存，不作为业务主键 |
| `RequestId` | 每次阿里云 API 调用返回 | 接口调用日志与排障 |

## 4. 场景与变量、标签配置

### 4.1 场景维护方式

糖尿病患者健康随访在阿里云“大模型场景管理”中按文本填写模式维护。慢管不修改阿里云话术或场景发布状态，只保存业务说明、场景关联和字段映射。

糖尿病场景的具体维护内容见：[糖尿病患者健康随访场景维护说明.md](糖尿病患者健康随访场景维护说明.md)。

### 4.2 `Extras` 与 `Summary` 的区别

```text
Extras
= 慢管 → 阿里云
= 通话前提供给机器人的患者上下文

Summary
= 阿里云 → 慢管
= 通话后机器人识别出的标签结论
```

#### Extras：下发变量，不是打标结果

慢管调用 `AssignJobs` 时，通过 `JobsJson.extras` 下发，例如：

```json
[
  { "key": "patient_name", "value": "张女士" },
  { "key": "followup_reason", "value": "本月糖尿病健康随访" },
  { "key": "recent_glucose_summary", "value": "近 7 天空腹血糖偏高" },
  { "key": "intervention_summary", "value": "控制主食、每周运动 3 次" }
]
```

建议一期变量：

| 变量名 | 说明 |
| --- | --- |
| `patient_name` | 患者姓名 |
| `manager_name` | 健管师姓名 |
| `organization_name` | 机构名称 |
| `followup_reason` | 本次随访原因 |
| `recent_glucose_summary` | 近期血糖摘要 |
| `intervention_summary` | 当前干预方案摘要 |
| `medication_summary` | 当前用药摘要 |
| `control_goal_summary` | 当前控制目标摘要 |
| `last_followup_summary` | 上次随访摘要 |

#### Summary：大模型通话后的标签结果

阿里云场景“标签描述”中配置的标签名称、标签描述和枚举标签值，是通话结束后需要返回给慢管的打标结果。糖尿病场景一期标签建议包括：

- 接听结论
- 随访完成
- 血糖监测
- 饮食执行
- 运动执行
- 用药依从
- 风险信号
- 执行障碍
- 人工跟进

理想回包示例：

```json
[
  { "SummaryName": "接听结论", "Content": "本人接听" },
  { "SummaryName": "随访完成", "Content": "已完成" },
  { "SummaryName": "血糖监测", "Content": "偏高" },
  { "SummaryName": "风险信号", "Content": "疑似低血糖表现" },
  { "SummaryName": "人工跟进", "Content": "需要跟进" }
]
```

上线前必须以真实测试电话验证：大模型场景标签实际返回路径、标签名称和标签值是否与慢管字段映射一致。`TagHits` 在文档中标识为旧画布返回字段，不作为大模型场景一期的固定依赖。

## 5. 发起设计

### 5.1 发起来源

- 患者详情的随访计划：健管师创建单个 AI 电话随访任务。
- AI 管理计划：按已设定的电话随访安排，自动生成患者 AI 电话随访任务。

在患者详情手工创建时，提供两个明确交互按钮：

```text
[立即发起外呼]     [加入待发起池]
```

- **立即发起外呼**：创建单人外呼批次，随后创建阿里 `JobGroup` 和 `Job`。
- **加入待发起池**：按场景、主叫号码和外呼策略归入待发起批次，由健管师统一发起。

### 5.2 任务下发链路

```text
慢管创建外呼批次
→ CreateJobGroup（传 InstanceId、ScriptId、策略、主叫号码）
→ 获得 JobGroupId
→ AssignJobs（传 JobGroupId、患者联系人、referenceId、Extras）
→ 获得 JobsId[]
→ 写回每条 AI 随访外呼记录
```

`AssignJobs` 的 `JobsJson` 中，每个元素对应一位患者。单次接口调用最多 99 位联系人；100 位患者可分两次下发到同一个 `JobGroup`，上线前须在测试实例验证同一任务组追加下发的实际行为。

## 6. AI 随访外呼记录：外呼状态

“外呼状态”是慢管每一条 AI 随访外呼记录面向健管师展示的状态，不直接展示阿里云技术状态、错误码或任务 ID。

| 外呼状态 | 业务含义 | 阿里云判断依据 | 页面说明 / 下一步 |
| --- | --- | --- | --- |
| 待发起 | 慢管已创建任务，尚未调用阿里云 | 尚无 `JobGroupId` 或 `JobId` | 可立即发起或加入待发起池 |
| 待外呼 | 已下发，等待首次拨打或下一次重拨 | `Job.Status=Scheduling` | 等待首次外呼；或“第 N 次未接通，将再次外呼” |
| 外呼中 | 正在拨号或通话 | `Job.Status=Executing`，或最新 `Task.Status=Executing` | 正在第 N 次外呼，不可重复发起 |
| 结果生成中 | 已正常结束通话，慢管正在获取结果 | 正常完成条件已满足，慢管尚未完成结果落库 | 通话结束，正在生成随访结果 |
| 已完成 | 正常完成随访，基础结果可查看 | `Job.Status=Succeeded`，最新 `Task.Status=SucceededFinish`，且 `HasAnswered=true`、`HasReachedEndOfFlow=true`；慢管已保存结果 | 查看随访结果、智能提炼 |
| 未完成 | 本次任务已结束，未形成有效随访结论且不再自动外呼 | 见下方“未完成原因映射” | 展示业务原因；可人工跟进或另建任务 |
| 已暂停 | 人工暂停后续外呼 | `Job.Status=Paused` | 可恢复或取消 |
| 已取消 | 人工明确终止任务 | `Job.Status=Cancelled` | 不再外呼 |

### 6.1 重拨判断规则

慢管不自行计算最大重拨次数，而是只读取阿里云 Job 的最终调度状态：

```text
最新一次 Task 未接通
+ Job.Status = Scheduling
= 待外呼（重试中）

最新一次 Task 未接通
+ Job.Status = Failed
= 未完成（未接通）
```

也就是说，重拨次数、重拨间隔和外呼时段由阿里云根据下发策略执行；慢管只同步并翻译阿里云结果。

### 6.2 未完成原因映射

| 业务结果说明 | 阿里云 Task / Job 判断依据 |
| --- | --- |
| 未接通 | `NoAnswer`、`Busy`、`NotConnected`、`PoweredOff` 等，且 Job 已结束不再调度 |
| 联系方式暂不可外呼 | `NotExist`、`EmptyNumber`、`OutOfService`、`InArrears` 等 |
| 本次暂不可外呼 | `ContactBlockList`、`PerDayCallCountLimit`、`VerificationCancelled` 等 |
| 患者拒访或无回应 | 拒识挂机、静默超时、用户无交互、用户挂机等已接通但未完成情形 |
| 已转人工 | `SucceededTransferByIntent` 或 `SucceededTransferAfterNoAnswer` |
| 通话中断 | `SucceededError` 或 `EndReason=ERROR`，且没有继续调度 |

> “需人工跟进”不是外呼状态。AI 电话即使已正常完成，只要标签识别出风险症状、调药咨询或患者要求人工联系，外呼状态仍为“已完成”，另加“需人工跟进”标识和健管师待办。

## 7. 随访结果状态

结果状态不展示“待回收 / 回收失败”等技术概念，仅用一个“随访结果”字段：

| 随访结果 | 阿里云判断依据 | 慢管判断依据 | 页面展示 |
| --- | --- | --- | --- |
| 暂无结果 | 电话未正常完成，或未形成有效随访结论 | 不发起结果拉取 / 无可展示数据 | 暂无随访结果 |
| 生成中 | `Job.Status=Succeeded`、最新 `Task.Status=SucceededFinish`、`HasAnswered=true`、`HasReachedEndOfFlow=true` | 已触发结果拉取，但文本、标签等尚未完整保存 | 随访结果生成中 |
| 已生成 | 阿里云已提供可拉取的通话结果 | 慢管已成功拉取并保存对话文本、标签和通话基础信息 | 查看随访结果 |

“AI 智能提炼”不是结果状态，而是结果详情页中的按需操作：

```text
随访结果：已生成
AI 提炼：未生成  [智能提炼]

随访结果：已生成
AI 提炼：已生成  [查看 AI 总结]
```

## 8. 开发接口清单

场景、话术、变量、标签、FAQ、语音及外呼策略均在阿里云控制台配置；慢管一期不调用这些配置类接口，也不做双向同步。以下为慢管服务端实际需要对接的接口。

| 接口名 | 地址 | 是否一期接入 | 用途 |
| --- | --- | --- | --- |
| `CreateJobGroup` | [接口文档](https://help.aliyun.com/zh/outboundbot/developer-reference/api-outboundbot-2019-12-26-createjobgroup) | 是 | 创建慢管外呼批次对应的阿里云 `JobGroup`。传入 `InstanceId`、`ScriptId`、外呼/重拨策略及主叫号码，保存返回的 `JobGroupId`。 |
| `AssignJobs` | [接口文档](https://help.aliyun.com/zh/outboundbot/developer-reference/api-outboundbot-2019-12-26-assignjobs) | 是 | 向 `JobGroup` 批量下发患者外呼任务。每位患者对应一个 `Job`；传慢管随访记录（或 AI 外呼记录）ID 作为 `referenceId`，通过 `extras` 传姓名、随访原因等话术变量。单次最多 99 人。 |
| `QueryJobsWithResult` | [接口文档](https://help.aliyun.com/zh/outboundbot/developer-reference/api-outboundbot-2019-12-26-queryjobswithresult) | 是 | 按 `JobGroup` 分页轮询患者任务最新状态，用于更新慢管 AI 外呼状态，以及判断是否需要拉取完整详情。 |
| `DescribeJob` | [接口文档](https://help.aliyun.com/zh/outboundbot/developer-reference/api-outboundbot-2019-12-26-describejob) | 是 | 获取单位患者 `Job` 的完整详情并落库：全部拨打尝试 `Tasks`、通话结束原因、对话文本 `Conversation`、大模型标签 `Summary`、传入变量 `Extras` 等。 |
| `DownloadRecording` | [接口文档](https://help.aliyun.com/zh/outboundbot/developer-reference/api-outboundbot-2019-12-26-downloadrecording) | 是 | 按实际通话 `TaskId` 获取录音下载信息；返回的是临时签名地址，健管师播放或下载时按需调用。 |
| `SuspendJobs` | [接口文档](https://help.aliyun.com/zh/outboundbot/developer-reference/api-outboundbot-2019-12-26-suspendjobs) | 是 | 暂停某个患者 `Job` 的后续外呼，对应慢管 AI 外呼状态“已暂停”。 |
| `ResumeJobs` | [接口文档](https://help.aliyun.com/zh/outboundbot/developer-reference/api-outboundbot-2019-12-26-resumejobs) | 是 | 恢复已暂停患者 `Job` 的后续外呼，对应“恢复外呼”操作。 |
| `CancelJobs` | [接口文档](https://help.aliyun.com/zh/outboundbot/developer-reference/api-outboundbot-2019-12-26-canceljobs) | 是 | 取消未通话或正在调度的患者 `Job`，对应慢管 AI 外呼状态“已取消”。已在通话中的任务取消无效，页面需提示“当前正在通话，暂不能取消”。 |
| `GetTaskByUuid` | [接口文档](https://help.aliyun.com/zh/outboundbot/developer-reference/api-outboundbot-2019-12-26-gettaskbyuuid) | 否（一期预留） | 查询单次通话的详情与对话。`DescribeJob` 已可返回一个 `Job` 下所有 `Task` 和对话，一期无需额外调用。 |

### 8.1 同步策略

```text
对非终态外呼批次
→ 后台按 JobGroupId 调用 QueryJobsWithResult
→ 通过 referenceId 定位慢管 AI 随访外呼记录
→ 仅对状态变化或已结束的 Job 调用 DescribeJob
→ 落库通话尝试、标签、对话文本
→ 更新外呼状态和随访结果状态
```

建议非终态批次每分钟同步一次；前端只读取慢管落库数据。患者或批次页面的“刷新状态”请求慢管立即执行一次同步，不让前端直接调用阿里云。

### 8.2 `QueryJobsWithResult`：批次状态摘要结构

```json
{
  "Jobs": {
    "PageNumber": 1,
    "PageSize": 100,
    "RowCount": 100,
    "List": [
      {
        "Id": "aliyun_job_xxx",
        "Status": "Scheduling",
        "JobFailureReason": null,
        "LatestTask": {
          "Status": "NoAnswer",
          "HasAnswered": false,
          "HasReachedEndOfFlow": false,
          "CallTime": 1780000000000,
          "CallDuration": 0,
          "Contact": {
            "ReferenceId": "slow_followup_task_001"
          }
        }
      }
    ]
  }
}
```

主要用于外呼状态、最近拨打事实和 `referenceId` 关联；不用于展示完整对话和全部通话历史。

### 8.4 `DownloadRecording`：录音数据结构

```json
{

    "VoiceSliceRecordingListJson": "[...]"
  }

```

| 字段 | 说明 |
| --- | --- |
| `SignatureUrl` | 临时录音播放 / 下载 URL，不能作为永久地址保存 |
| `FileName` | 录音文件名 |
| `VoiceSliceRecordingListJson` | 分段录音列表；原字段是 JSON 字符串，慢管需二次解析 |

## 9. 结果展示与 PDCA

### 9.1 健管师结果详情

当随访结果为“已生成”时，详情页以业务结论优先展示：

```text
患者与随访身份
→ 外呼状态与随访结果
→ 结构化标签结果
→ 健管师按需触发 AI 随访总结
→ 风险 / 人工跟进提示
→ 通话录音、完整对话和原始标签证据
```

慢管不把“已接通”直接展示为“随访完成”；只有场景流程正常完成且基础结果已保存，才显示“已完成”。

### 9.2 AI 提炼与后续动作

- 健管师在结果详情页手动点击“智能提炼”。
- AI 基于结构化标签和原始对话文本生成随访小结、关键点、风险提示、执行障碍和建议人工跟进事项。
- AI 不直接诊断疾病、调整处方或自动修改干预方案。
- 风险症状、执行障碍、患者诉求、人工处理结果等，进入后续饮食方案、运动方案、健康周报和管理计划生成时的参考资料。
- 一期仅生成调整建议和待办，由健管师确认后执行，不自动修改患者干预方案。

## 10. 联调与验收重点

1. 验证 `InstanceId + ScriptId` 与慢管随访类型映射正确。
2. 验证 `AssignJobs` 下发的变量与阿里云场景变量同名且可在通话中使用。
3. 验证 100 人批次拆分下发、同一 `JobGroup` 追加下发和 `referenceId` 回写关联。
4. 验证首次未接通后 `Job.Status=Scheduling` 时，慢管展示“待外呼（重试中）”；最终 `Job.Status=Failed` 时展示“未完成”。
5. 验证正常完成、拒访、忙碌、非本人、转人工、风险症状、用户挂机、系统中断等外呼状态映射。
6. 用真实测试电话核验阿里云大模型标签的实际返回路径及 `SummaryName / Content` 映射。
7. 验证 `DescribeJob` 返回的多次 `Tasks[]`、对话文本和 `TaskId` 能完整落库。
8. 验证 `DownloadRecording` 临时录音地址的播放、权限和有效期处理。
9. 验证健管师手动 AI 提炼和结果进入干预方案、管理计划、健康周报的上下文。
