# AI 健管师 Agent Harness 设计

日期：2026-08-04

## 1. 目标

AI 健管师面向健管师提供三类连续能力：

1. 查询患者健康档案和相关健康上下文；
2. 从单个患者或责任人群中发现需要管理的患者问题，说明问题及证据，并提出管理建议；
3. 在健管师选择建议后，生成一个或多个患者专属交付物草稿。

首期的产品闭环是：

```text
找到该管的人
→ 说明患者有什么问题及证据
→ 提出管理建议
→ 健管师选择
→ 生成可审阅的干预方案或创作型作品草稿
```

AgentScope 提供 Agent、工具、记忆、运行轨迹等通用能力。本设计定义与慢管业务相关的 Harness，包括扫描入口、权限、上下文装配、问题合并、证据引用、人工控制、安全边界和评测。

## 2. 首期范围

### 2.1 包含

- 单患者手动扫描；
- 按条件选择人群后手动扫描；
- 按健管师责任范围进行定时人群扫描；
- 读取慢管系统患者基础档案、专病档案、近期指标、用药、饮食、运动和指标上传记录；
- 使用固定规则与 Agent 综合分析发现患者问题；
- 持久化患者问题，合并重复扫描产生的相同问题；
- 展示患者问题、证据、重要程度及管理建议；
- 健管师选择一个或多个管理建议后生成交付物；
- 生成干预方案草稿或创作型作品草稿；
- 所有交付物绑定具体患者和患者问题；
- 记录来源引用、模型版本、规则版本和运行轨迹；
- 评测运行可靠性、问题可信度、证据可靠性和产出可用性。

### 2.2 不包含

- 患者待办、任务提醒和任务完成状态；
- 向慢管系统写入干预方案或其他业务数据；
- 自动触达患者；
- 自动执行管理动作；
- 基于患者数据变更事件的实时扫描；
- 通用作品素材库或跨患者作品复用；
- 将所有来源预处理成统一的医学原子事实库或知识图谱。

未来取得慢管系统写接口后，在现有流程末端增加人工确认、执行适配器、结果验证和审计，不改造前面的扫描、判断和生成主链。

## 3. 产品核心模型

产品只向健管师呈现三个核心概念：

```text
患者问题 → 管理建议 → 交付物
```

### 3.1 患者问题

患者问题回答：

- 哪个患者存在什么问题；
- 判断证据是什么；
- 问题是否重要或紧急；
- 哪些内容是客观数据，哪些是规则判断或 Agent 推断；
- 问题首次和最近一次被发现的时间。

相同患者的相同问题在后续扫描中更新证据和趋势，不重复创建。问题明显恶化或出现关键新证据时，重新进入待查看状态。

最小状态为：

```text
待查看 → 已忽略
      → 已采纳 → 已生成交付物
```

状态用于管理扫描结果，不代表患者待办。

### 3.2 管理建议

管理建议回答：

- 针对当前患者问题建议做什么；
- 为什么建议这样做；
- 建议生成哪类交付物。

一个患者问题可以有多个管理建议。Agent 可以主动提出建议，但健管师选择后才生成完整交付物。

### 3.3 交付物

首期交付物分为：

- 结构化干预方案草稿；
- 创作型作品草稿，例如患者宣教材料、沟通内容和阶段总结。

一次选择可以生成多个交付物。每个交付物必须绑定患者、患者问题和被选择的管理建议，并保留内容版本、编辑记录和审核状态。

## 4. 总体架构

采用分阶段混合型 Harness：

```text
扫描触发
→ 权限及范围校验
→ 候选患者筛选
→ 患者健康上下文装配
→ 固定规则判断 + Agent 综合分析
→ 患者问题归并和保存
→ Agent 提出管理建议
→ 健管师选择
→ Agent 生成交付物草稿
→ 草稿箱编辑与审核
```

确定性程序负责：

- 租户、机构、健管师和患者数据权限；
- 扫描触发方式、范围、分页和批次；
- 慢管 API 调用、超时和失败隔离；
- 固定规则和高风险兜底；
- 原始来源登记及引用校验；
- 相同患者问题归并；
- 患者问题与交付物状态；
- 人工选择控制点；
- 日志、追踪、成本和评测记录。

AgentScope Agent 负责：

- 基于多类健康材料发现规则以外的复杂患者问题；
- 判断是否需要继续调用只读工具补查数据；
- 综合材料解释患者为什么需要管理；
- 输出患者问题、判断说明和来源引用位置；
- 提出管理建议；
- 根据健管师选择生成交付物内容。

首期不采用多个业务 Agent 自由讨论的组织型架构。分析和生成可以使用不同的 Agent 配置，但都运行在确定性的阶段控制中。

## 5. 扫描入口和执行流程

### 5.1 单患者手动扫描

健管师在患者场景中触发。Harness 校验患者属于当前可访问范围，加载标准健康摘要，再由规则和 Agent 分析。

### 5.2 人群手动扫描

健管师选择患者筛选条件后触发。Harness 使用慢管患者列表及指标上传记录接口筛选候选患者，分页处理并逐个分析。

### 5.3 定时人群扫描

系统按配置周期扫描健管师责任人群。每个健管师、机构和租户的扫描范围隔离。一个患者失败不影响其他患者或整个批次完成。

### 5.4 后续事件触发

未来慢管系统提供稳定的数据事件或消息机制后，可将患者指标更新等事件转换为新的扫描入口。事件触发仍复用同一条分析链路。

## 6. 患者健康上下文

采用混合装配方式：

1. Harness 默认准备标准患者健康摘要；
2. Agent 判断信息不足时，可以调用经过授权的只读工具查询明细；
3. 只查询当前任务所需的最小数据，不默认加载全部历史；
4. 每次补充查询都重新校验租户、机构、健管师和患者范围。

标准摘要可包含基础档案、专病档案、近期健康指标和数据新鲜度。药品明细、指定时间段饮食运动、历史指标上传记录等作为按需查询工具。

AgentScope Memory 不替代业务患者档案。患者事实以慢管系统和当次登记的来源材料为准；Memory 只保存本次 Agent 工作所需的对话与运行状态。

## 7. 规则与 Agent 混合判断

固定风险和明确阈值由规则稳定召回；复杂趋势、跨材料关系和管理机会由 Agent 补充发现。

每个患者问题记录发现来源：

- 规则发现；
- Agent 发现；
- 规则与 Agent 共同支持。

固定高风险规则优先。Agent 可以补充解释和建议，但不得删除、覆盖或降低固定规则给出的风险等级。

## 8. 来源、证据引用和关联推理

### 8.1 原始来源登记

任何供 Agent 使用的材料先登记为不可修改的来源。来源包括：

- 慢管 API 响应；
- Chatbox 消息或人工粘贴文本；
- 上传文件及其可检索文本；
- 图片及 OCR 结果。

来源至少记录：

- `source_id`；
- 来源类型；
- 患者、租户和机构；
- 来源系统记录 ID、消息 ID 或文件 ID；
- 数据发生时间和读取时间；
- 原始内容受控快照或可回查定位；
- 内容哈希；
- 当前访问权限。

不得把所有来源预先转换为高度结构化的原子事实。结构化慢管数据和非结构化文本都直接作为大模型可理解的上下文材料。

### 8.2 模型输出引用位置

Agent 输出患者问题时，同时输出每项判断使用的来源和定位信息：

- API 数据：来源 ID、业务记录 ID、JSONPath 或字段路径；
- Chatbox：消息 ID、字符起止位置或完整消息引用；
- 文件：文件 ID、页码、段落或字符位置；
- 图片：图片 ID、OCR 文本位置或区域坐标。

### 8.3 Harness 引用校验

Harness 在保存患者问题前校验：

- 来源属于当前患者及权限范围；
- 定位信息真实存在；
- 引用的数字、单位、时间和限定词没有被模型篡改；
- 判断说明没有把推断伪装成原始事实。

校验成功后，为实际使用的引用生成内部 `evidence_id`。未被使用的原始材料不需要提前生成证据记录。

### 8.4 关联推理

患者问题保存简化的推理链：

```text
来源引用 → 中间判断 → 患者问题 → 管理建议
```

中间判断可以同时引用多个来源，并标记证据的作用是支持、补充或冲突。推断必须与原始来源引用分开保存；推断不能在后续运行中被当作新的客观事实。

不要求使用图数据库。普通关系表或 JSON 结构能够保存结论与引用关系即可。

## 9. 重复问题归并

定时扫描不能反复生成相同提醒。Harness 根据患者、问题类型及有效时间范围识别是否为同一问题：

- 首次发现时创建患者问题；
- 后续扫描更新证据、最近发现时间、趋势和重要程度；
- 变化不大时不重复提醒；
- 明显恶化或出现关键新证据时重新进入待查看；
- 已忽略的问题也可以因显著变化重新出现。

问题归并属于内部机制，不作为新的产品概念展示给健管师。

## 10. 人工控制

首期采用草拟型自治：

- Agent 可以自动扫描、发现患者问题和提出管理建议；
- Agent 不自动生成所有完整交付物；
- 健管师先查看患者问题和证据，再选择一个或多个建议；
- 只有被选择的建议才触发交付物生成；
- 交付物保存在患者作品草稿箱，可编辑和审核；
- 首期不自动写回慢管系统，也不触达患者。

未来可按动作风险逐步增加自动执行能力，但执行权限不由 Agent 自行决定。

## 11. 异常处理

### 11.1 数据不完整

系统明确记录缺少的材料。Agent 只能基于已取得的数据判断。关键资料缺失时不生成患者问题，返回本次无法完成分析及缺失原因。

### 11.2 引用校验失败

患者问题不得入库。可以把校验错误反馈给 Agent 修正一次；再次失败则放弃该候选问题，并记录脱敏运行错误。

### 11.3 单患者失败

人群扫描中只失败当前患者，不中断整个批次。批次结束后记录成功、跳过和失败数量。

### 11.4 模型超时或输出不合规

执行有限次数重试。仍失败时保留运行结果和错误分类，但不生成空白、无引用或猜测性患者问题。

### 11.5 慢管接口鉴权失败

按现有对接约定仅执行一次重新鉴权及原请求重试，禁止无限重试。生产环境使用机器账号的最小必要权限，不长期依赖健管师用户会话凭证。

## 12. 安全与隐私

- 所有慢管 API 只能由 Agent 后端调用；
- 每次读取都校验租户、机构、健管师和患者数据范围；
- 患者健康信息按最小范围查询并最短时间缓存；
- 权限变化后不得继续展示已无权访问的来源原文；
- 日志只记录链路 ID、来源 ID、HTTP 状态、业务码和脱敏错误；
- 不记录账号密码、Token、患者完整档案或完整作品内容；
- Chatbox 人工材料记录提供者及时间，明确其为人工提供或患者自述，不能冒充客观设备事实；
- 所有患者问题和交付物记录使用的模型、Prompt、规则和工具版本。

## 13. AgentScope 能力映射

AgentScope 只负责模型工作所需的通用运行能力；业务 Harness 决定何时调用 Agent、给它什么材料、允许调用什么工具，以及如何校验和保存结果。

### 13.1 逐环节映射

| 业务环节 | AgentScope 能力 | 使用方式 | 仍需自建的 Harness |
| --- | --- | --- | --- |
| 单患者、人群、定时扫描触发 | 不依赖 AgentScope | 由业务接口、页面操作和调度系统发起 | 扫描入口、责任人群范围、分页、批次、幂等和失败隔离 |
| 候选患者筛选 | 首期不调用 Agent | 后端直接调用慢管患者列表和指标上传记录接口 | 筛选策略、规则、数据范围和优先级；不让模型自由决定扫描谁 |
| 标准健康摘要装配 | `Msg`、Formatter | Harness 取得数据后，转换为带来源标识的 Agent 输入消息；Formatter 适配具体模型 | 来源登记、患者数据选择、摘要结构、脱敏和上下文大小控制 |
| Agent 按需补查患者明细 | `Toolkit`、Tool、ReActAgent 的工具循环 | 把药品明细、饮食运动、历史指标等封装成只读工具；ReActAgent 判断需要时调用 | 工具内再次校验租户、机构、健管师和患者；注入服务端身份；限制查询范围和次数 |
| 工具权限、校验和审计 | Toolkit Tool Middleware | 在工具执行前后做输入校验、鉴权、限流、缓存、错误转换、耗时和调用日志 | 业务授权规则和患者范围不是 AgentScope 自动提供，必须由应用实现；不得相信模型传入的租户或身份参数 |
| 规则发现患者问题 | 不依赖 AgentScope | 固定高风险和明确阈值由普通规则服务执行 | 规则内容、版本、优先级、命中证据和不可被模型降级的约束 |
| Agent 补充发现复杂问题 | `ReActAgent`、Model、Formatter、Toolkit | ReActAgent 综合标准摘要，必要时补查只读工具，输出患者问题候选、判断说明和引用位置 | 分析 Prompt、允许发现的问题边界、最大步骤、超时、成本及停止条件 |
| 输出患者问题和管理建议 | ReActAgent Structured Output、`Msg.metadata` | 使用 Pydantic 等结构约束问题、建议、重要程度、推理说明和来源定位；结构化结果放入消息元数据或业务返回值 | 业务字段定义、医疗语义校验、固定风险合并，以及最终是否允许入库 |
| 原始来源登记 | 不依赖 AgentScope | AgentScope 消息只携带 `source_id` 和所需内容 | 来源快照、哈希、数据发生时间、读取时间、权限和回查定位由业务来源库保存 |
| 引用真实性校验 | AgentScope 只负责返回结构化定位 | Agent 输出 `source_id + locator + usage` | Harness 校验来源归属、位置、数字、单位、时间和限定词；校验后才生成 `evidence_id` |
| 重复患者问题合并 | 不依赖 AgentScope | 不使用 Agent Memory 判断是否重复 | 业务数据库按患者、问题类型和有效时间归并，更新证据、趋势、优先级和状态 |
| 人工查看和选择建议 | 可选使用 Agent State 和中断能力，但首期不依赖 | 首期由业务页面读取患者问题，健管师选择建议后发起新的生成请求 | 人工控制点、选择记录、用户身份、问题状态和请求幂等 |
| 生成干预方案或作品 | ReActAgent、Structured Output、Message 多模态内容 | 使用独立的生成配置，根据患者问题、证据、被选建议和作品要求生成一个或多个交付物 | 交付物模板、内容校验、版本、编辑、审核、患者关联和草稿箱持久化 |
| 任务内上下文 | InMemoryMemory 或数据库 Memory | 保存单次分析或生成运行中的消息，支持多轮工具调用和必要的上下文压缩 | Memory 不是患者档案，也不是患者问题库；运行结束后由业务库保存正式结果 |
| 中断与恢复 | Agent State、`state_dict`、`load_state_dict`、ReActAgent 中断处理 | 对耗时生成或交互式创作保存 Agent 的运行状态，并在中断后恢复 | 业务运行 ID、权限再次校验、过期策略和恢复后的结果幂等 |
| 运行追踪 | Tracing、OpenTelemetry、模型用量和工具调用事件 | 记录模型调用、工具调用、耗时、Token、错误和运行链路 | 患者敏感数据脱敏、业务指标、模型/Prompt/规则版本以及审计保留策略 |
| 成本控制 | Agent 最大步骤和工具限制；可选 Budget Control Middleware | 限制单次 Agent 循环、工具调用数量和 Token 预算 | 不同扫描入口的业务预算、批量并发、超预算降级和运营告警 |
| 对外服务和部署 | AgentScope Service、Agent-as-a-Service、OpenTelemetry | 可以将分析或生成 Agent 作为服务部署，也可直接嵌入现有后端 | 业务 API、鉴权、任务队列、数据库、调度、租户隔离和发布运维体系 |
| 未来慢管写入执行 | Toolkit 写工具、Tool Middleware、Agent 中断或人工确认 | 为通过审批的动作单独提供受控写工具；调用前拦截确认，调用后返回结构化结果 | 动作权限、审批、幂等键、写后验证、补偿、审计和风险分级；分析 Agent 默认不得拥有写工具 |

### 13.2 两类 Agent 配置

首期可以复用 AgentScope 的同一种 `ReActAgent` 实现，但使用两个独立配置，不需要组成自由协作的多 Agent 团队：

| 配置 | 输入 | 可用工具 | 输出 |
| --- | --- | --- | --- |
| 分析配置 | 标准健康摘要、来源材料、规则结果 | 只读慢管查询工具 | 患者问题候选、引用位置、管理建议 |
| 生成配置 | 已保存患者问题、已验证证据、被选管理建议、交付物要求 | 首期通常无需慢管工具；必要时仅开放只读查询 | 一个或多个干预方案或创作型作品草稿 |

两个配置由业务流程串联。分析 Agent 不能自行启动生成 Agent；生成必须由健管师选择触发。

### 13.3 首期不需要启用的 AgentScope 能力

- **Agent Team、MsgHub 和多 Agent 自由协作**：当前业务流程已明确，增加协调 Agent、档案 Agent、风险 Agent 会增加延迟、成本和调试难度；先使用分阶段的两个 Agent 配置。
- **RAG 作为患者档案主存储**：慢管 API 是患者事实来源，不能用向量检索替代精确查询。只有长篇指南、宣教知识或大量上传材料需要语义检索时再引入 RAG。
- **Long-term Memory 保存患者事实**：患者档案、患者问题、证据和作品必须进入业务数据库。长期记忆只适合未来保存经过治理的交互偏好，不能成为医疗事实的权威来源。
- **Workspace 作为用户的“云主机”或作品草稿箱**：文本和结构化交付物直接保存到业务草稿箱。只有未来需要运行代码、处理文件或生成复杂文件时，才在后台使用隔离 Workspace；不向用户暴露主机或文件系统心智。
- **MCP 作为必选接入层**：现有慢管 API 可以直接封装为 Python Tool。只有需要把同一组工具开放给多个 Agent 框架或团队时，再考虑 MCP 标准化。
- **Plan 模块驱动固定扫描流程**：扫描、权限、规则、保存和人工控制是确定性业务流程，不应让模型动态规划；Plan 只适合交付物创作等真正开放的复杂子任务。

### 13.4 责任边界结论

```text
业务 Harness
  负责：触发、范围、权限、规则、来源、引用校验、去重、状态、人工控制、持久化和评测

AgentScope
  负责：模型调用、ReAct 循环、只读工具调用、结构化输出、任务内记忆、中断恢复和技术追踪

大模型
  负责：综合理解、关联推理、问题解释、管理建议和交付物创作
```

患者问题、交付物、来源登记和权限属于业务数据，应保存在业务持久层，不依赖 AgentScope 会话 Memory 作为唯一存储。

## 14. 评测与验收

### 14.1 运行可靠性

- 慢管接口查询成功率；
- 单患者和人群扫描完成率；
- 单患者失败隔离正确性；
- 扫描耗时、模型调用次数和成本；
- 定时扫描重复执行的幂等性。

### 14.2 患者问题可信度

- 问题识别准确性；
- 重要问题和固定高风险问题召回；
- 无依据问题比例；
- 相同问题正确合并率；
- 数据不足时正确停止判断的比例。

### 14.3 证据可靠性

- 引用可定位率；
- 数字、单位、时间和限定词保真率；
- 客观事实与 Agent 推断区分正确率；
- 跨患者、跨机构引用错误数；
- 人工材料来源类型标记正确率。

### 14.4 产品可用性

- 健管师查看和采纳管理建议的比例；
- 被采纳建议生成交付物的比例；
- 健管师对交付物的修改幅度；
- 健管师有用性评分；
- 被忽略问题的抽样合理性。

### 14.5 评测方法

上线前建立脱敏真实病例评测集，覆盖常见问题、无问题、关键数据缺失、高风险、来源冲突和人工文本材料。由健管专家标注合理患者问题、关键证据、可接受建议和不可接受结论。

引用定位、数字保真和输出结构使用自动评测；医学合理性、管理价值和交付物可用性由健管专家复核。上线后持续记录查看、忽略、采纳、生成和修改行为，并对被采纳与被忽略结果同时抽样复核。

跨患者或跨机构数据泄露、伪造引用、固定高风险规则被 Agent 覆盖属于阻断性问题，不能由平均得分抵消。

## 15. 已确认的设计决策

- 首期采用草拟型，未来预留分级自治；
- 单患者、人群和定时扫描使用一套统一 Harness；
- 首期做到查询、扫描、分析、建议和交付物生成；
- 待办不进入首期范围；
- 一个患者问题可以产生多个管理建议和多个交付物；
- 采用规则与 Agent 混合判断；
- 先展示患者问题和建议，健管师选择后才生成完整交付物；
- 患者上下文采用标准摘要加 Agent 按需只读查询；
- 所有交付物绑定具体患者和患者问题；
- 患者问题持久化并合并重复扫描结果；
- 产品核心概念只保留患者问题、管理建议和交付物；
- 来源材料统一登记，但不预建高度结构化的原子事实库；
- Agent 输出来源定位，Harness 校验后保存实际使用的证据引用；
- 采用分阶段混合型架构，不使用首期多 Agent 自由组织架构。
