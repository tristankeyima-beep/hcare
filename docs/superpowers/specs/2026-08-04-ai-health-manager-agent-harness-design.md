# AI 健管师 Agent Harness 设计

日期：2026-08-04

## 1. 目标

AI 健管师面向健管师提供三类连续能力：

1. 查询患者健康档案和相关健康上下文；
2. 从单个患者或责任人群中发现需要管理的患者问题，说明问题及证据，并提出管理建议；
3. 在健管师选择建议后，生成一个或多个患者专属交付物草稿。

首期的产品闭环是：

```text
健管师用自然语言提出管理目标
→ Agent 制定并执行查询计划
→ 找到该管的人
→ 说明患者有什么问题及证据
→ 提出管理建议
→ 健管师选择
→ 生成可审阅的干预方案或创作型作品草稿
```

AgentScope 提供 Agent、工具、记忆、运行轨迹等通用能力。本设计定义与慢管业务相关的 Harness，包括自然语言任务理解、查询计划、扫描入口、权限、上下文装配、问题合并、证据引用、人工控制、安全边界和评测。

## 2. 首期范围

### 2.1 包含

- 通过 Chatbox 接收健管师的自然语言管理指令；
- 理解单患者分析、人群找人、继续追问和交付物生成等任务；
- 根据自然语言、当前页面、当前患者和对话上下文制定可审计的查询计划；
- 通过慢管只读工具执行查询计划，并根据返回结果继续补查；
- 单患者自然语言查询和分析；
- 按自然语言条件进行人群筛选和分析；
- 按健管师责任范围进行定时人群扫描；
- 读取慢管系统患者基础档案、专病档案、近期指标、用药、饮食、运动和指标上传记录；
- 使用固定规则与 Agent 综合分析发现患者问题；
- 持久化患者问题，合并重复扫描产生的相同问题；
- 展示患者问题、证据、重要程度及管理建议；
- 健管师选择一个或多个管理建议后生成交付物；
- 生成干预方案草稿或创作型作品草稿；
- 所有交付物绑定具体患者和患者问题；
- 记录来源引用、模型版本、规则版本和运行轨迹；
- 评测运行可靠性、问题可信度、证据可靠性和产出可用性。

### 2.2 不包含

- 患者待办、任务提醒和任务完成状态；
- 向慢管系统写入干预方案或其他业务数据；
- 自动触达患者；
- 自动执行管理动作；
- 基于患者数据变更事件的实时扫描；
- 通用作品素材库或跨患者作品复用；
- 将所有来源预处理成统一的医学原子事实库或知识图谱。

未来取得慢管系统写接口后，在现有流程末端增加人工确认、执行适配器、结果验证和审计，不改造前面的扫描、判断和生成主链。

## 3. 产品核心模型

产品只向健管师呈现三个核心概念：

```text
患者问题 → 管理建议 → 交付物
```

### 3.1 患者问题

患者问题回答：

- 哪个患者存在什么问题；
- 判断证据是什么；
- 问题是否重要或紧急；
- 哪些内容是客观数据，哪些是规则判断或 Agent 推断；
- 问题首次和最近一次被发现的时间。

相同患者的相同问题在后续扫描中更新证据和趋势，不重复创建。问题明显恶化或出现关键新证据时，重新进入待查看状态。

最小状态为：

```text
待查看 → 已忽略
      → 已采纳 → 已生成交付物
```

状态用于管理扫描结果，不代表患者待办。

### 3.2 管理建议

管理建议回答：

- 针对当前患者问题建议做什么；
- 为什么建议这样做；
- 建议生成哪类交付物。

一个患者问题可以有多个管理建议。Agent 可以主动提出建议，但健管师选择后才生成完整交付物。

### 3.3 交付物

首期交付物分为：

- 结构化干预方案草稿；
- 创作型作品草稿，例如患者宣教材料、沟通内容和阶段总结。

一次选择可以生成多个交付物。每个交付物必须绑定患者、患者问题和被选择的管理建议，并保留内容版本、编辑记录和审核状态。

## 4. 总体架构

采用分阶段混合型 Harness：

```text
健管师自然语言指令
→ 理解任务、患者范围、时间范围和问题目标
→ ReAct 制定查询计划
→ Harness 校验权限、能力和成本边界
→ Toolkit 调用慢管只读工具
→ 获得候选患者和健康材料
→ 患者健康上下文装配
→ 固定规则判断 + Agent 综合分析
→ 患者问题归并和保存
→ Agent 提出管理建议
→ 健管师选择
→ Agent 生成交付物草稿
→ 草稿箱编辑与审核
```

确定性程序负责：

- 租户、机构、健管师和患者数据权限；
- 向 Agent 提供当前页面、当前患者和当前登录健管师等可信业务上下文；
- 校验 Agent 查询计划中的患者范围、工具范围、分页上限、最大候选数和成本预算；
- 扫描触发方式、范围、分页和批次；
- 慢管 API 调用、超时和失败隔离；
- 固定规则和高风险兜底；
- 原始来源登记及引用校验；
- 相同患者问题归并；
- 患者问题与交付物状态；
- 人工选择控制点；
- 日志、追踪、成本和评测记录。

AgentScope Agent 负责：

- 理解健管师自然语言中的任务、患者指代、时间范围、问题目标、排序和数量限制；
- 结合 Toolkit 工具描述制定查询计划；
- 在计划允许范围内选择和调用慢管只读工具，并根据结果调整后续查询；
- 结合对话 Memory 理解“第一个”“这几个人”“再看看用药”等连续指令；
- 基于多类健康材料发现规则以外的复杂患者问题；
- 判断是否需要继续调用只读工具补查数据；
- 综合材料解释患者为什么需要管理；
- 输出患者问题、判断说明和来源引用位置；
- 提出管理建议；
- 根据健管师选择生成交付物内容。

首期不采用多个业务 Agent 自由讨论的组织型架构。分析和生成可以使用不同的 Agent 配置，但都运行在确定性的阶段控制中。

## 5. 自然语言入口、查询计划和执行流程

### 5.1 常见自然语言任务

首期至少支持四类指令：

| 任务 | 示例 | 目标 |
| --- | --- | --- |
| 单患者分析 | “帮我看看张三最近的情况”“这个患者当前最需要关注什么” | 识别患者，查询相关健康材料并发现问题 |
| 人群找人 | “看看我管理的患者里谁最需要干预”“找出最近一周血压控制不好的患者” | 将结构化人群条件和语义问题条件结合，找到值得管理的人 |
| 连续追问 | “为什么是这几个人”“再看看第一个人的用药”“把证据不足的去掉” | 复用当前候选集合、患者问题和已查询材料继续分析 |
| 生成交付物 | “针对王阿姨这个问题生成干预方案”“改成患者容易理解的版本” | 引用已确认的患者问题和管理建议生成或修改草稿 |

### 5.2 自然语言任务理解

Agent 结合用户原话和可信业务上下文，识别：

- 任务类型：单患者分析、人群找人、连续追问或生成交付物；
- 患者指代：明确患者、姓名或手机号、当前页面患者、当前候选集合；
- 人群范围：当前健管师、疾病、风险标记和风险分层；
- 时间范围：今天、最近一周、最近三个月等；
- 问题目标：血压控制不好、需要干预、用药依从性可能有问题等；
- 数据重点：指标、用药、饮食、运动或完整上下文；
- 排序和数量：按严重程度、只看前十名等；
- 期望输出：患者列表、患者问题、管理建议或交付物。

当前登录健管师、租户、机构、当前页面患者等身份信息只能由慢管应用后端注入，不能从模型生成结果中获取或信任。

### 5.3 查询计划

分析 Agent 使用 ReAct 推理和 Toolkit 工具描述，将自然语言目标转成可审计的查询计划。查询计划至少说明：

```json
{
  "taskType": "find_patients_with_problems",
  "patientScope": {
    "owner": "current_health_manager",
    "disease": "hypertension",
    "riskMark": null
  },
  "timeRange": "recent_7_days",
  "structuredFilters": [],
  "semanticConditions": ["blood_pressure_not_well_controlled"],
  "plannedTools": ["search_managed_patients", "get_recent_indicators"],
  "sort": "problem_severity",
  "limit": 10
}
```

查询计划区分两类条件：

- 可下推条件：患者姓名或手机号、签约健管师、红黄绿标、高中低危层、指标上传时间、指标类型和数据来源，可直接映射为慢管 API 参数；
- 语义条件：“控制不好”“最需要干预”“情况变差”“依从性可能有问题”等，不能直接映射为 API 参数，需要先查询候选患者材料，再由规则和 Agent 判断。

查询计划不是允许 Agent 任意访问数据。Harness 在执行前校验：

- 患者和人群是否在当前健管师授权范围内；
- 工具是否为当前阶段允许的只读工具；
- 时间范围、分页、候选数、深度分析人数和 Token 预算是否在上限内；
- 患者姓名存在歧义时是否需要先让健管师选择；
- 计划是否要求当前慢管接口不具备的能力。

计划不通过时，Harness 返回可解释错误，由 Agent 缩小范围、改用已有工具或向健管师追问，不能绕过校验。

### 5.4 查询计划执行与用户介入策略

查询计划采用“先计划、后执行、滚动修正”的方式：

```text
自然语言指令
→ ReAct 生成初始查询计划
→ Harness 校验
→ 执行只读工具
→ 根据结果判断继续、停止或询问用户
→ 必要时更新计划并再次校验
```

查询计划应保存：

- 用户目标和任务类型；
- 患者或人群范围；
- 时间范围；
- 可下推条件和语义条件；
- 计划使用的工具及每一步目的；
- Agent 使用的默认假设；
- 尚未解决的歧义；
- 当前接口不支持的条件；
- 预计候选规模、深度分析人数和成本；
- 是否需要用户介入。

#### 5.4.1 ReAct 可以自行继续的条件

同时满足以下条件时，可以继续调用工具而不打断健管师：

- 患者身份和授权范围明确；
- 下一次调用仍在已经批准的查询计划内；
- 工具为当前阶段允许的只读工具；
- 调用与用户目标直接相关，预计能够补充当前缺失信息；
- 查询范围、分页、候选数、步骤和 Token 仍在预算内；
- 不会扩大到新的患者、人群、机构或敏感数据范围；
- 不是对同一工具和相同参数的无效重复调用。

以下技术动作默认不询问用户：安全分页、一次鉴权重试、来源登记、日期转换、结果去重以及不改变用户目标的补充查询。

#### 5.4.2 ReAct 应停止查询的条件

满足任一条件时停止继续调用工具，并回答、报告部分结果或说明无法完成：

- 已经取得足以回答用户目标的材料，并能为患者问题提供可定位引用；
- 后续允许的工具不会明显增加有效信息；
- 连续查询没有得到新材料；
- 当前慢管接口不支持所需能力；
- 关键数据无法获得，继续推理会变成无依据猜测；
- 达到最大工具步骤、候选数、深度分析人数、时间或 Token 预算；
- 用户中断、取消或改变目标；
- 工具或权限错误在允许重试后仍未恢复。

停止不等于强行给结论。材料不足时应明确区分“未发现问题”和“现有数据不足以判断”。

#### 5.4.3 必须询问健管师的条件

以下情况不能由 Agent 自行假设：

| 原因码 | 场景 | 应提供的备选方案 |
| --- | --- | --- |
| `AMBIGUOUS_PATIENT` | 同名患者、患者指代不明确 | 展示完成消歧所需的最少信息，让健管师选择 |
| `AMBIGUOUS_SCOPE` | “看看哪些患者需要关注”等范围过大或目标不清 | 提供高风险、近期有新数据、指定疾病、分批处理等范围选项 |
| `AMBIGUOUS_CONCEPT` | “依从性差”等存在多种业务含义 | 提供用药、测量、生活方式或综合管理等含义选项 |
| `UNSUPPORTED_FILTER` | 慢管接口不能直接支持用户要求 | 说明限制，提供近似筛查、缩小患者范围、补充材料或取消 |
| `SCOPE_TOO_LARGE` | 候选患者或预计成本超过上限 | 提供按风险、近期数据、批次或明确人数缩小范围的选项 |
| `DATA_INSUFFICIENT` | 缺少形成可靠判断的关键材料 | 提供扩大时间范围、补查其他数据、上传材料或暂不判断 |
| `CONFLICTING_EVIDENCE` | 慢管数据与人工材料明显冲突 | 提供以人工材料作为补充、扩大查询、人工确认或暂不判断 |
| `PARTIAL_FAILURE` | 部分接口失败且可能影响结论 | 提供重试、基于已取得材料继续并标记局限、或停止 |
| `PERMISSION_REQUIRED` | 下一步需要扩大患者或数据范围 | 只能请求用户选择有权范围；不得由 Agent 自行扩权 |

用户介入采用结构化结果：

```json
{
  "nextAction": "ask_user",
  "reasonCode": "AMBIGUOUS_PATIENT",
  "question": "找到多位同名患者，请选择要分析的人。",
  "options": [
    {"id": "P001", "label": "张三，男，62岁，手机号尾号1234"},
    {"id": "P002", "label": "张三，女，55岁，手机号尾号5678"}
  ],
  "resumeToken": "opaque-token"
}
```

Harness 在展示前校验选项不越权、不过度暴露患者信息。用户选择后通过 `resumeToken` 恢复原查询计划，不重新从头推理。

询问文本必须给出可执行选项，不能只说“条件不明确”“暂不支持”或“数据不足”。没有合理选项时才允许开放文本补充。

#### 5.4.4 默认值与低打扰原则

只有低影响、可见且可撤销的默认值可以由 Agent 采用，例如当前页面患者、当前登录健管师和产品已定义的“最近”时间范围。使用默认值时应在结果中展示，例如“已查看最近30天记录”，允许健管师继续调整。

患者身份、机构范围、关键医学概念和会显著影响成本或结果的人群范围不能静默使用默认值。

#### 5.4.5 ReAct 下一步动作协议

每轮 ReAct 只输出以下一种动作：

```text
call_tool   调用一个或一组批准范围内的只读工具
ask_user    暂停并向健管师提供结构化选择
answer      当前材料足以回答或形成患者问题
stop        当前能力不足、预算耗尽或错误无法恢复
```

调用工具时保存可审计的操作理由和预期信息增益，不保存或展示模型内部思维链：

```json
{
  "nextAction": "call_tool",
  "tool": "get_medication_summary",
  "purpose": "补查当前患者的用药记录",
  "expectedInformationGain": "判断血压控制问题是否存在相关用药线索",
  "withinApprovedPlan": true
}
```

### 5.5 Toolkit 工具设计与通用契约

首期慢管接口包装为面向业务语义的只读工具，而不是把原始 HTTP 接口直接暴露给模型：

| Tool | 慢管接口 | 用途 |
| --- | --- | --- |
| `search_managed_patients` | `POST /contract-patient/page` | 按姓名、手机号、签约健管师、疾病分标和分层查询患者 |
| `search_indicator_updates` | `POST /patient-indicator-monitor/page` | 按上传时间、指标类型、数据来源和风险条件查询指标更新患者 |
| `get_basic_archive` | `GET /patient-icpr/basic-archive` | 获取基础档案 |
| `get_chronic_archive` | `GET /patient-icpr/chronic-archive` | 获取专病档案 |
| `get_recent_indicators` | `GET /patient-icpr/measure-indicator` | 获取最近健康指标 |
| `get_medication_summary` | `GET /patient-recent-drug/group-by-drug/page` | 获取按药品分组的用药记录 |
| `get_medication_detail` | `GET /patient-recent-drug/group-by-drug-detail/page` | 补查指定药品取药记录 |
| `get_diet_records` | `GET /patient-diet-sport/list-diet` | 查询指定时间段饮食记录 |
| `get_sport_records` | `GET /patient-diet-sport/list-sport` | 查询指定时间段运动记录 |

工具描述必须告诉 Agent 何时使用、支持哪些筛选、返回什么、数据时间含义和限制。Tool Middleware 在服务端注入租户、机构、健管师身份和访问令牌；这些字段不允许由模型自由传入。

当前接口文档中的 `dmScale*`、`htmScale*`、`htnScale*` 疾病含义存在不一致，正式启用相应工具参数前必须通过实际响应确认映射。

所有 Tool 遵守以下通用契约：

- 只返回当前授权范围内的数据；
- 租户、机构、健管师身份和 Token 由服务端注入；
- 模型只提交业务参数，不接触凭证或可信身份参数；
- 返回结果带 `source_id`、数据时间、查询时间和分页信息；
- API 无数据、接口失败和无权限使用不同状态表达；
- 工具结果说明“数据表示什么、不表示什么”；
- 工具不直接生成患者问题或医学结论；
- 分页、超时、重试、缓存和最大结果数由 Harness 控制；
- 原始业务码和敏感错误只进入脱敏审计，不直接展示给用户或模型。

#### 5.5.1 `search_managed_patients`

**能做什么**

- 在当前授权范围内按患者姓名或手机号查找患者；
- 按签约健管师筛选责任患者；
- 按高血压、糖尿病的分标和风险分层筛选候选患者；
- 为单患者消歧或人群分析提供候选集合。

**不能做什么**

- 不能判断患者是否“控制不好”“需要干预”“依从性差”；
- 不能证明患者当前存在某个健康问题；
- 不能绕过当前健管师权限查询其他患者。

**何时调用**

- 用户只有姓名或手机号，尚未取得明确 `patientId`；
- 用户提出人群找人指令，且包含接口支持的签约、分标或分层条件；
- 需要确认某患者是否属于当前可管理范围。

**何时不调用**

- 已经有经过权限校验的 `patientId`，且任务只涉及该患者；
- 用户只是在追问当前患者已有问题或生成交付物；
- 用户条件完全属于语义判断，且没有可用于缩小人群的结构化条件时，不应声称该工具能够直接筛出结果。

**返回语义**

返回满足查询条件的候选患者分页列表。出现在结果中只表示患者满足列表条件，不表示其已被发现存在健康问题。

**限制**

- 必须分页；正式返回字段、总数和稳定排序规则仍需联调确认；
- `dmScale*` 与 `htmScale*` 的疾病映射需通过实际响应确认；
- 同名患者必须由健管师消歧；
- 大结果集只能作为候选集合，不能自动触发无限制深度分析。

#### 5.5.2 `search_indicator_updates`

**能做什么**

- 按指标上传时间查询近期更新记录；
- 按患者姓名或手机号、风险条件、指标类型和数据来源筛选；
- 找出近期有血糖、血压、血脂、糖化血红蛋白、BMI 或腰围更新的候选患者。

**不能做什么**

- 不能仅凭“有上传记录”判断指标异常；
- 不能替代完整的历史趋势查询；
- 不能把“患者自行上传”解释为数据一定真实或异常；
- 不能直接判断患者需要干预。

**何时调用**

- 用户明确询问近期上传、更新或指定指标类型的患者；
- 查询目标需要根据数据新鲜度缩小候选范围；
- 定时扫描需要按上传时间查找近期变化。

**何时不调用**

- 用户只询问明确患者的当前综合情况，且最近指标接口已经能满足；
- 用户需要无上传记录患者或长期未测患者时，不能仅调用本工具得出完整名单，必须结合责任患者集合反向判断；
- 用户需要判断指标是否控制良好时，仍需获取具体指标数据并分析。

**返回语义**

返回满足上传时间和过滤条件的指标更新记录或相关患者。它证明发生过数据上传或更新，不证明临床异常或管理问题。

**限制**

- `createTimeStart`、`createTimeEnd` 使用毫秒时间戳，时区和边界包含规则需确认；
- 返回中是否包含稳定记录 ID、`patientId` 和健管师权限范围需联调确认；
- `dmScale*`、`htnScale*` 的疾病映射存在文档不一致；
- 多页扫描必须使用重叠时间窗和业务去重，避免遗漏或重复。

#### 5.5.3 `get_basic_archive`

**能做什么**

- 获取指定患者的基础档案，支持身份确认和基础健康上下文装配。

**不能做什么**

- 不能代表患者当前健康状态；
- 不能独立证明患者需要干预；
- 不能覆盖 Chatbox 中经确认的新信息，存在冲突时应并列呈现并说明时间。

**何时调用**

- 首次分析明确患者，需要建立基础上下文；
- 患者人口学或基础档案信息会影响当前问题判断；
- 需要确认材料是否属于同一患者。

**何时不调用**

- 当前运行已经取得同一版本的基础档案，且没有数据刷新需要；
- 生成交付物时已保存经过验证的必要患者上下文。

**返回语义**

返回慢管系统当前保存的基础档案快照，表示系统记录的内容，不保证所有字段最新或完整。

**限制**

- 当前只验证过该接口成功返回档案数据，完整字段语义和更新时效仍需以正式响应契约为准；
- 只能按 `patientId` 查询；
- 属于敏感健康信息，必须最小化传入模型的字段。

#### 5.5.4 `get_chronic_archive`

**能做什么**

- 获取指定患者的专病档案，补充慢病诊断、管理和专病相关背景。

**不能做什么**

- 不能仅凭档案字段判断当前控制效果；
- 不能替代近期指标、用药和生活方式材料；
- 不能把历史档案内容自动视为当前仍然有效。

**何时调用**

- 用户询问某慢病的综合情况；
- 人群筛选后需要对候选患者进行专病深度分析；
- 当前问题需要疾病背景才能解释。

**何时不调用**

- 当前问题与专病信息无关，基础材料已经足够；
- 同一运行已经取得相同档案版本。

**返回语义**

返回慢管系统记录的专病档案快照，是分析背景而不是当前问题结论。

**限制**

- 当前接口文档未给出完整响应字段和更新时效；
- 只能按 `patientId` 查询；
- Agent 必须保留档案数据发生或更新时间，避免把历史事实写成当前事实。

#### 5.5.5 `get_recent_indicators`

**能做什么**

- 获取指定患者最近的健康指标，用于快速了解当前指标概况；
- 为进一步查询和患者问题分析提供方向。

**不能做什么**

- “最近指标”不等于完整时间序列；
- 单次或最近一次指标不能自动证明长期控制情况；
- 不能仅凭缺少最近指标断言患者没有测量或依从性差。

**何时调用**

- 分析患者当前总体情况；
- 用户询问最近血压、血糖等指标；
- 需要判断是否继续查询指标上传记录或其他材料。

**何时不调用**

- 用户明确要求长时间趋势，而该接口不能提供所需历史范围；
- 同一运行中已经取得相同时间点的最近指标。

**返回语义**

返回慢管系统定义的“最近健康指标”快照。每项指标必须保留测量时间和来源；没有返回不能直接解释为患者从未测量。

**限制**

- 当前文档未说明各指标的历史条数、最近值选择规则和来源；
- 趋势判断需要其他历史数据支持；
- 异常判断需结合规则、患者背景和数据时间。

#### 5.5.6 `get_medication_summary`

**能做什么**

- 按药品分组查询患者近期用药或取药记录；
- 帮助 Agent 了解系统中记录了哪些药品，并决定是否补查某个药品明细；
- 支持按药品名称过滤和分页。

**不能做什么**

- 取药记录不能证明患者实际服药；
- 没有记录不能直接证明患者未用药；
- 不能单独判断用药依从性、疗效或调整药物方案。

**何时调用**

- 患者问题可能与用药情况相关；
- 用户明确询问用药、取药或可能的用药连续性线索；
- 需要确定后续应查询哪个药品明细。

**何时不调用**

- 当前问题与用药无关，其他材料已足够；
- 用户要求确认实际服药行为时，必须说明该工具只能提供有限线索；
- 已经获得当前任务所需的药品分组信息。

**返回语义**

返回慢管系统中按药品分组的近期记录，是用药或取药线索，不是实际服药事实或依从性结论。

**限制**

- 使用 `patientId`、页码、页大小和可选药品名；
- 返回时间范围、记录来源和“用药/取药”的准确业务含义需依据正式响应确认；
- 依从性判断必须结合其他来源并使用“可能”等限定表达。

#### 5.5.7 `get_medication_detail`

**能做什么**

- 查询指定药品、厂家和规格对应的患者取药明细；
- 为药品连续性和时间关系分析提供更细记录。

**不能做什么**

- 不能证明患者按医嘱服用；
- 不能推断医生处方意图、剂量调整或停药原因；
- 不能用于模型自行给出药物调整建议。

**何时调用**

- 已通过用药分组结果确定具体药品、厂家和规格；
- 当前问题确实需要查看该药品的时间明细；
- 用户明确要求查看指定药品记录。

**何时不调用**

- 尚未取得准确药品名、厂家和规格；
- 只是了解患者有哪些药品时，先调用分组工具；
- 与当前患者问题无关或预计不会增加有效信息。

**返回语义**

返回指定药品组合的取药记录明细，只能作为时间和连续性的线索。

**限制**

- 药品名、厂家、规格必须来自可信查询结果或用户明确输入，不能由 Agent 猜测；
- 字符编码、规格格式和分页需要工具层统一处理；
- 记录缺失的业务含义需谨慎解释。

#### 5.5.8 `get_diet_records`

**能做什么**

- 查询指定患者和日期范围内慢管系统记录的饮食数据；
- 为生活方式问题和交付物个性化提供材料。

**不能做什么**

- 没有饮食记录不能证明患者没有进食、没有执行饮食管理或依从性差；
- 记录内容不能自动证明完整、准确；
- 不能脱离患者背景直接形成营养诊断。

**何时调用**

- 用户明确询问饮食；
- 患者问题或管理建议需要结合近期饮食记录；
- 生成饮食相关交付物需要个性化材料。

**何时不调用**

- 当前问题与饮食无关；
- 用户没有给出时间范围且产品默认范围会显著影响结果时，应先确认或展示默认值；
- 同一时间范围的数据已经取得。

**返回语义**

返回指定时间段内已记录的饮食内容，表示“系统有这些记录”，不表示该时间段全部真实饮食行为。

**限制**

- 当前接口文档中的请求 URL 与原始载荷日期范围不一致，调用时必须使用查询计划统一计算的日期；
- 只能按 `patientId` 和日期范围查询；
- 长时间范围应分段或限制，避免上下文膨胀。

#### 5.5.9 `get_sport_records`

**能做什么**

- 查询指定患者和日期范围内慢管系统记录的运动数据；
- 为生活方式分析和运动相关交付物提供材料。

**不能做什么**

- 没有运动记录不能证明患者没有运动或执行差；
- 不能自动证明运动强度、持续时间或设备数据完全准确；
- 不能脱离疾病和身体情况直接给出高风险运动建议。

**何时调用**

- 用户明确询问运动；
- 当前患者问题需要结合运动情况；
- 生成运动相关干预方案或宣教材料需要个性化内容。

**何时不调用**

- 当前目标与运动无关；
- 时间范围不明确且默认范围会显著影响判断；
- 同一时间范围的数据已经取得。

**返回语义**

返回指定时间段内已记录的运动内容，表示系统中存在这些记录，不代表完整的真实运动行为。

**限制**

- 只能按 `patientId` 和日期范围查询；
- 返回字段、数据来源和记录完整性需以正式响应为准；
- 长时间范围应分段或限制，避免模型上下文和接口负载过大。

### 5.6 单患者自然语言执行

当指令明确当前患者或 `patientId` 时，Agent 在权限校验后直接查询所需材料。当只有姓名或手机号时，先调用 `search_managed_patients`：零个结果则说明未找到；一个结果继续分析；多个结果必须让健管师选择，不能由 Agent 猜测。

### 5.7 人群自然语言执行

人群找人先把可下推条件交给患者列表或指标上传工具缩小范围，再对候选患者查询语义条件所需材料。例如“找出我管理的高血压患者中最近一周血压控制不好的前十个人”：

```text
当前健管师 + 高血压 → 查询候选患者
→ 查询候选患者最近一周血压材料
→ 规则 + Agent 判断“控制不好”
→ Harness 按问题严重程度排序
→ 返回前十名及各自证据
```

结构化筛选只负责缩小候选范围；“值得管”“控制不好”等语义判断必须由后续分析完成。

### 5.8 连续追问

AgentScope Memory 保存本次对话正在讨论的候选患者集合、当前患者、已查询来源和患者问题引用，使 Agent 能理解“第一个”“这几个人”“再看用药”等指令。正式患者问题和来源仍保存在业务数据库，不以 Memory 作为权威存储。

### 5.9 定时人群扫描

系统按配置周期扫描健管师责任人群。每个健管师、机构和租户的扫描范围隔离。一个患者失败不影响其他患者或整个批次完成。

定时扫描没有临时用户原话，但可以使用预先保存并经健管师确认的自然语言管理目标或结构化查询计划，复用同一套计划校验、慢管查询和问题分析链路。

### 5.10 后续事件触发

未来慢管系统提供稳定的数据事件或消息机制后，可将患者指标更新等事件转换为新的扫描入口。事件触发仍复用同一条分析链路。

## 6. 患者健康上下文

采用混合装配方式：

1. Harness 默认准备标准患者健康摘要；
2. Agent 判断信息不足时，可以调用经过授权的只读工具查询明细；
3. 只查询当前任务所需的最小数据，不默认加载全部历史；
4. 每次补充查询都重新校验租户、机构、健管师和患者范围。

标准摘要可包含基础档案、专病档案、近期健康指标和数据新鲜度。药品明细、指定时间段饮食运动、历史指标上传记录等作为按需查询工具。

AgentScope Memory 不替代业务患者档案。患者事实以慢管系统和当次登记的来源材料为准；Memory 只保存本次 Agent 工作所需的对话与运行状态。

## 7. 规则与 Agent 混合判断

固定风险和明确阈值由规则稳定召回；复杂趋势、跨材料关系和管理机会由 Agent 补充发现。

每个患者问题记录发现来源：

- 规则发现；
- Agent 发现；
- 规则与 Agent 共同支持。

固定高风险规则优先。Agent 可以补充解释和建议，但不得删除、覆盖或降低固定规则给出的风险等级。

## 8. 来源、证据引用和关联推理

### 8.1 原始来源登记

任何供 Agent 使用的材料先登记为不可修改的来源。来源包括：

- 慢管 API 响应；
- Chatbox 消息或人工粘贴文本；
- 上传文件及其可检索文本；
- 图片及 OCR 结果。

来源至少记录：

- `source_id`；
- 来源类型；
- 患者、租户和机构；
- 来源系统记录 ID、消息 ID 或文件 ID；
- 数据发生时间和读取时间；
- 原始内容受控快照或可回查定位；
- 内容哈希；
- 当前访问权限。

不得把所有来源预先转换为高度结构化的原子事实。结构化慢管数据和非结构化文本都直接作为大模型可理解的上下文材料。

### 8.2 模型输出引用位置

Agent 输出患者问题时，同时输出每项判断使用的来源和定位信息：

- API 数据：来源 ID、业务记录 ID、JSONPath 或字段路径；
- Chatbox：消息 ID、字符起止位置或完整消息引用；
- 文件：文件 ID、页码、段落或字符位置；
- 图片：图片 ID、OCR 文本位置或区域坐标。

### 8.3 Harness 引用校验

Harness 在保存患者问题前校验：

- 来源属于当前患者及权限范围；
- 定位信息真实存在；
- 引用的数字、单位、时间和限定词没有被模型篡改；
- 判断说明没有把推断伪装成原始事实。

校验成功后，为实际使用的引用生成内部 `evidence_id`。未被使用的原始材料不需要提前生成证据记录。

### 8.4 关联推理

患者问题保存简化的推理链：

```text
来源引用 → 中间判断 → 患者问题 → 管理建议
```

中间判断可以同时引用多个来源，并标记证据的作用是支持、补充或冲突。推断必须与原始来源引用分开保存；推断不能在后续运行中被当作新的客观事实。

不要求使用图数据库。普通关系表或 JSON 结构能够保存结论与引用关系即可。

## 9. 重复问题归并

定时扫描不能反复生成相同提醒。Harness 根据患者、问题类型及有效时间范围识别是否为同一问题：

- 首次发现时创建患者问题；
- 后续扫描更新证据、最近发现时间、趋势和重要程度；
- 变化不大时不重复提醒；
- 明显恶化或出现关键新证据时重新进入待查看；
- 已忽略的问题也可以因显著变化重新出现。

问题归并属于内部机制，不作为新的产品概念展示给健管师。

## 10. 人工控制

首期采用草拟型自治：

- Agent 可以自动扫描、发现患者问题和提出管理建议；
- Agent 不自动生成所有完整交付物；
- 健管师先查看患者问题和证据，再选择一个或多个建议；
- 只有被选择的建议才触发交付物生成；
- 交付物保存在患者作品草稿箱，可编辑和审核；
- 首期不自动写回慢管系统，也不触达患者。

未来可按动作风险逐步增加自动执行能力，但执行权限不由 Agent 自行决定。

## 11. 异常处理

### 11.1 数据不完整

系统明确记录缺少的材料。Agent 只能基于已取得的数据判断。关键资料缺失时不生成患者问题，返回本次无法完成分析及缺失原因。

### 11.2 引用校验失败

患者问题不得入库。可以把校验错误反馈给 Agent 修正一次；再次失败则放弃该候选问题，并记录脱敏运行错误。

### 11.3 单患者失败

人群扫描中只失败当前患者，不中断整个批次。批次结束后记录成功、跳过和失败数量。

### 11.4 模型超时或输出不合规

执行有限次数重试。仍失败时保留运行结果和错误分类，但不生成空白、无引用或猜测性患者问题。

### 11.5 慢管接口鉴权失败

按现有对接约定仅执行一次重新鉴权及原请求重试，禁止无限重试。生产环境使用机器账号的最小必要权限，不长期依赖健管师用户会话凭证。

## 12. 安全与隐私

- 所有慢管 API 只能由 Agent 后端调用；
- 每次读取都校验租户、机构、健管师和患者数据范围；
- 患者健康信息按最小范围查询并最短时间缓存；
- 权限变化后不得继续展示已无权访问的来源原文；
- 日志只记录链路 ID、来源 ID、HTTP 状态、业务码和脱敏错误；
- 不记录账号密码、Token、患者完整档案或完整作品内容；
- Chatbox 人工材料记录提供者及时间，明确其为人工提供或患者自述，不能冒充客观设备事实；
- 所有患者问题和交付物记录使用的模型、Prompt、规则和工具版本。

## 13. AgentScope 能力映射

AgentScope 只负责模型工作所需的通用运行能力；业务 Harness 决定何时调用 Agent、给它什么材料、允许调用什么工具，以及如何校验和保存结果。

### 13.2 两类 Agent 配置

首期可以复用 AgentScope 的同一种 `ReActAgent` 实现，但使用两个独立配置，不需要组成自由协作的多 Agent 团队：

| 配置 | 输入 | 可用工具 | 输出 |
| --- | --- | --- | --- |
| 分析配置 | 健管师自然语言、可信会话上下文、来源材料、规则结果 | 患者筛选、档案和明细等只读慢管工具 | 查询计划、患者问题候选、引用位置、管理建议 |
| 生成配置 | 已保存患者问题、已验证证据、被选管理建议、交付物要求 | 首期通常无需慢管工具；必要时仅开放只读查询 | 一个或多个干预方案或创作型作品草稿 |

两个配置由业务流程串联。分析 Agent 不能自行启动生成 Agent；生成必须由健管师选择触发。

### 13.3 首期不需要启用的 AgentScope 能力

- **Agent Team、MsgHub 和多 Agent 自由协作**：当前业务流程已明确，增加协调 Agent、档案 Agent、风险 Agent 会增加延迟、成本和调试难度；先使用分阶段的两个 Agent 配置。
- **RAG 作为患者档案主存储**：慢管 API 是患者事实来源，不能用向量检索替代精确查询。只有长篇指南、宣教知识或大量上传材料需要语义检索时再引入 RAG。
- **Long-term Memory 保存患者事实**：患者档案、患者问题、证据和作品必须进入业务数据库。长期记忆只适合未来保存经过治理的交互偏好，不能成为医疗事实的权威来源。
- **Workspace 作为用户的“云主机”或作品草稿箱**：文本和结构化交付物直接保存到业务草稿箱。只有未来需要运行代码、处理文件或生成复杂文件时，才在后台使用隔离 Workspace；不向用户暴露主机或文件系统心智。
- **MCP 作为必选接入层**：现有慢管 API 可以直接封装为 Python Tool。只有需要把同一组工具开放给多个 Agent 框架或团队时，再考虑 MCP 标准化。
- **Plan 模块接管固定业务流程**：自然语言查询需要 ReAct 制定查询计划，但权限、规则、保存和人工控制仍是确定性流程，不能由模型动态改写。首期查询计划使用 Structured Output 和工具循环即可，不要求启用更重的自主任务规划。

### 13.4 责任边界结论

```text
业务 Harness
  负责：可信会话上下文、查询计划校验、权限、规则、来源、引用校验、去重、状态、人工控制、持久化和评测

AgentScope
  负责：自然语言理解、查询计划、模型调用、ReAct 循环、只读工具调用、结构化输出、任务内记忆、中断恢复和技术追踪

大模型
  负责：理解管理目标、选择查询路径、综合材料、关联推理、问题解释、管理建议和交付物创作
```

患者问题、交付物、来源登记和权限属于业务数据，应保存在业务持久层，不依赖 AgentScope 会话 Memory 作为唯一存储。

## 14. 评测与验收

### 14.1 运行可靠性

- 自然语言任务类型和患者指代识别正确率；
- 查询计划可执行率和工具选择正确率；
- 无效、重复和越界工具调用比例；
- 应询问时正确暂停的比例，以及不必要打扰用户的比例；
- 用户选择后正确恢复原查询计划的比例；
- 慢管接口查询成功率；
- 单患者和人群扫描完成率；
- 单患者失败隔离正确性；
- 扫描耗时、模型调用次数和成本；
- 定时扫描重复执行的幂等性。

### 14.2 患者问题可信度

- 问题识别准确性；
- 重要问题和固定高风险问题召回；
- 无依据问题比例；
- 相同问题正确合并率；
- 数据不足时正确停止判断的比例。

### 14.3 证据可靠性

- 引用可定位率；
- 数字、单位、时间和限定词保真率；
- 客观事实与 Agent 推断区分正确率；
- 跨患者、跨机构引用错误数；
- 人工材料来源类型标记正确率。

### 14.4 产品可用性

- 用户介入问题能否说明原因并提供可执行选项；
- 用户完成一次澄清所需的平均轮数；
- 健管师查看和采纳管理建议的比例；
- 被采纳建议生成交付物的比例；
- 健管师对交付物的修改幅度；
- 健管师有用性评分；
- 被忽略问题的抽样合理性。

### 14.5 评测方法

上线前建立脱敏真实病例评测集，覆盖常见问题、无问题、关键数据缺失、高风险、来源冲突和人工文本材料。由健管专家标注合理患者问题、关键证据、可接受建议和不可接受结论。

引用定位、数字保真和输出结构使用自动评测；医学合理性、管理价值和交付物可用性由健管专家复核。上线后持续记录查看、忽略、采纳、生成和修改行为，并对被采纳与被忽略结果同时抽样复核。

跨患者或跨机构数据泄露、伪造引用、固定高风险规则被 Agent 覆盖属于阻断性问题，不能由平均得分抵消。

## 15. 已确认的设计决策

- 首期采用草拟型，未来预留分级自治；
- 产品主入口是健管师自然语言指令，而不是后台扫描配置；
- 分析 Agent 使用 ReAct 推理和 Toolkit 工具描述制定可审计的查询计划；
- Harness 必须在执行前校验查询计划的权限、能力、规模和成本边界；
- ReAct 每轮只能选择调用工具、询问用户、回答或停止四类动作之一；
- 患者身份、范围、概念、能力或成本存在关键歧义时必须暂停，并向健管师提供可执行备选方案；
- 低影响默认值可以减少打扰，但必须可见、可修改，不能静默扩大患者或机构范围；
- 可结构化条件下推到慢管接口，“控制不好”“值得干预”等语义条件由规则和 Agent 分析；
- 连续对话支持当前患者、候选集合和已查材料的指代复用；
- 单患者、人群和定时扫描使用一套统一 Harness；
- 首期做到查询、扫描、分析、建议和交付物生成；
- 待办不进入首期范围；
- 一个患者问题可以产生多个管理建议和多个交付物；
- 采用规则与 Agent 混合判断；
- 先展示患者问题和建议，健管师选择后才生成完整交付物；
- 患者上下文采用标准摘要加 Agent 按需只读查询；
- 所有交付物绑定具体患者和患者问题；
- 患者问题持久化并合并重复扫描结果；
- 产品核心概念只保留患者问题、管理建议和交付物；
